## 3. Implementation order (tests first)

### 3.1 Before the change

There is no `Cargo.toml` anywhere in the repository. `cargo build` and
`cargo test` fail with `could not find 'Cargo.toml' in /home/mike/dev/lido
or any parent directory`, and `cargo metadata` fails identically. All
three DoD clauses fail for the same trivial reason.

### 3.2 Step 1 — documents first, then git

Reordered from the original draft, which had `git init` first. Everything
§6 decided is a *documentation* change, and none of it is under version
control yet, so the documents are brought into agreement before the
repository exists rather than through a sequence of PRs against an empty
`main`.

1. Amend `doc/design.md` §2 per §2 "Modified" above — the `xtask` crate
   and the corrected `doc/` tree.
2. Fold §6's answers into §§1–5 of this file, so the plan committed to
   git is internally consistent rather than self-correcting in an
   appendix. §6 stays, as the record of what was asked and answered.
3. Move `doc/development-generic.md` out of the working tree — it is not
   tracked and is going to a different project (§6.8). Do this before
   step 5, not after.
4. `git init`, ensure the initial branch is `main` (slice 0.2 puts branch
   protection on that name).
5. Initial commit on `main`: the five remaining `doc/*.md` files (§6.8),
   plus `doc/slices/0.1-workspace-skeleton.md`.
6. Add the remote once it exists. Not a blocker — steps 4–5 and all of
   §§3.3–3.6 work on a purely local repository, and `git remote add` +
   `git push -u` can follow at any point.

development.md §7 says slice 0.1 is "done by hand rather than through the
loop", because nothing else in that document works before the repo
exists. This plan now takes that literally: no branch, no PR, no review
gate for 0.1 itself (§6.9). The loop starts at slice 0.2, which has a
`main` to branch from, a PR template to fill, and CI to fail against.

### 3.3 Step 2 — the smallest thing that lets a test run

Create the virtual `Cargo.toml` with **one** member, `xtask`, plus that
crate's `Cargo.toml` and stub `src/main.rs`. At this point `cargo build`
and `cargo test` succeed and run zero tests.

The first member is `xtask` rather than `crates/lido-cli` because the
test in step 3 lives there; starting with `lido-cli` would mean creating
a second crate before the first test can be written.

### 3.4 Step 3 — write the failing test

Write `xtask/tests/workspace_layout.rs` in full, listing all nine
expected package names as a constant:

```rust
/// design.md §2 names these crates. The DoD for slice 0.1 is that
/// `cargo metadata` lists every one of them.
const EXPECTED_PACKAGES: [&str; 9] = [
    "lido-cddl", "lido-ir", "lido-codegen",
    "lido-codegen-cpp", "lido-codegen-java", "lido-codegen-rust",
    "lido-cli", "lido-runtime", "xtask",
];
```

`xtask` is in the list because the assertion below is set equality and
`cargo metadata` reports every workspace member. Leaving it out would
fail the test — correctly, since an unannounced crate is exactly what
that assertion exists to catch.

Each test shells out once to `cargo metadata --no-deps --format-version 1`
using `env!("CARGO")` as the binary and `env!("CARGO_MANIFEST_DIR")` to
locate the workspace, and parses the `packages` array.

| Test | Asserts | Names |
|---|---|---|
| `crates_match_design_section_2` | the set of package names equals `EXPECTED_PACKAGES` — **exactly**, so both a missing crate and an unannounced extra crate fail | DoD clause 3 |
| `req_dep_010_every_package_is_mit_licensed` | `LICENSE` exists at the workspace root and every package's `license` is `"MIT"` | REQ-DEP-010 |
| `req_nfr_030_every_package_targets_rust_2021` | every package's `edition` is `"2021"`, and `rust-toolchain.toml` contains a `channel` pinned to an explicit version rather than `stable`/`beta`/`nightly` | REQ-NFR-030 |
| `req_arch_040_no_backend_depends_on_another_backend` | no `lido-codegen-{cpp,java,rust}` package lists another as a dependency | REQ-ARCH-040 |

Every test carries a doc comment naming the `REQ-*` ID or DoD clause it
covers, per development.md §3.2.

**Run it. It fails**, and the failure message is the useful one: eight of
nine expected packages are missing from `cargo metadata`.

### 3.5 Step 4 — make it pass

1. Create the eight remaining crates and add them to `members`.
2. Fill in `[workspace.package]` — `edition = "2021"`, `license = "MIT"`,
   `version`, `repository`, `rust-version = "1.97.1"` — and inherit in

3. Add `rust-toolchain.toml` with the pinned channel (§6.1).
4. Add `LICENSE`, `README.md`, `.gitignore`.
5. Add the process scaffolding: `CLAUDE.md`, `doc/decisions.md`,

- One-line description of the project and the current phase.
- Pointers to `doc/specs.md`, `doc/design.md`, `doc/code-style.md`,
  `doc/plan.md`, `doc/development.md`, `doc/decisions.md`, and (once it

## 4. Open questions for review

**All nine are answered in §6.** They are left here as drafted — the
question is the record of what was uncertain before the gate, and §6 is
the record of what was decided at it. Where an answer contradicts the
wording below (question 4 in particular), §6 wins.

1. **Exact toolchain pin.** REQ-NFR-030 pins the *edition* (2021), not
   the compiler version, and nothing in the specs picks one. Recent Rust
   defaults new crates to edition 2024, so the edition must be set
   explicitly regardless. Which stable version — and do we pin
   `rust-version` (MSRV) to the same value or leave it lower? Also:
   should `rust-toolchain.toml` list `targets`, given slice 2.7 needs a
   `no_std` target?
2. **Copyright holder and remote URL.** The MIT text needs
   `Copyright (c) <year> <holder>` — your name, or an org? And the git
   remote: does the GitHub repo exist yet, and under which owner/name?
   (The repo name also pre-empts part of specs.md §16 Q1.)
3. **What `lido-cli`'s stub `main` does.** `fn main() {}` (silent, exit
   0) versus printing a "not implemented" line to stderr with a non-zero
   exit. The first keeps the crate genuinely empty; the second is
   honest to anyone who runs it before slice 5.4.
4. **Where the workspace-layout test lives.** A virtual workspace root
   can't host `tests/`, so the options are (a) `crates/lido-cli/tests/`
   — recommended, no new crate, no design.md change; (b) a dedicated
   `xtask` crate, which is a common Rust idiom but **would add a crate
   not named in design.md §2**, so it needs a docs PR first; (c) make
   the root a real package rather than virtual, which changes the shape
   design.md §2 shows. Also: this test needs to parse JSON.
   `serde_json` as a dev-dependency (MIT/Apache-2.0, satisfies
   REQ-DEP-020) is the clean way; the alternative is substring matching
   on the metadata output, which is dependency-free but cannot reliably
   attribute a `license` field to a package. Recommend `serde_json`, but
   note it lands one slice *before* the `cargo deny` gate exists.
5. **Does `doc/decisions.md` ship with entries, or empty?** Slice 0.2
   writes the first real entry (the reference runner). If the toolchain
   pin from question 1 is a decision worth surviving — and I think it is,
   since every later slice inherits it — it wants to be `D-001` in this
   slice. Your call whether 0.1 opens the log or just creates it.
6. **Commit `Cargo.lock`?** Convention says yes for a workspace that
   produces a binary (`lido-cli`), and slice 0.2's `cargo deny` and CI
   reproducibility both benefit. Confirming because it affects every
   future PR diff.
7. **Add the REQ-ARCH-040 dependency guard now, or later?** It is about
   ten lines in the same test file and it makes "no backend depends on
   another backend" mechanical from the first commit rather than from
   whenever someone remembers. Against: plan.md does not cite
   REQ-ARCH-040 for this slice, and today the check passes vacuously.
8. **Which existing docs are tracked?** `doc/` currently holds
   `specs.md`, `design.md`, `code-style.md`, `plan.md`,
   `development.md`, and `development-generic.md`. Is
   `development-generic.md` a working draft that stays out of the repo,
   or does it ship?
9. **Process for this slice's own PR.** development.md §7 says 0.1 is
   done by hand outside the loop; there is no protected `main` and no CI
   until 0.2. Do you want a real PR against a freshly created remote
   (reviewable, but the gates it would run don't exist yet), or a direct

The answers have been **folded into §§1–5**, which now describe the

record of what was asked, what was chosen, and why — that reasoning does

Answers are numbered to match §4.

### 6.1 — Toolchain pin (§4 Q1) → **D-001**

**Decision.** `rust-toolchain.toml` pins `channel = "1.97.1"` — an exact
three-part version, with `components = ["rustfmt", "clippy"]` and
`profile = "minimal"`. `[workspace.package]` sets
`rust-version = "1.97.1"`. No `targets` key.

**Rationale.** REQ-NFR-030 requires pinning to a specific version rather
than tracking current stable, and §3.4's test asserts the channel is not
`stable`/`beta`/`nightly`. 1.97.1 (2026-07-14) is current stable; the
1.92.0 already installed locally is five releases behind on day one, and
starting stale only defers the bump into Phase 2 where lint churn would
land on top of real code. The pin matters less for compilation than for
`rustfmt` and `clippy`, whose output changes between releases — it is
what makes `cargo fmt --check` and `cargo clippy -- -D warnings` agree
across the three CI platforms from slice 0.2.

**Consequences.** A toolchain bump is its own PR, expected to carry fmt
and clippy churn, and is never folded into a feature slice.
`rust-version` equal to the pin is self-enforcing but rises with every
bump; `lido-runtime`'s MSRV is the one that will actually matter to
consumers (REQ-RT-110 targets lag stable), so it is set independently and
below the pin when the crate is published in slice 10.1 — which will
require an MSRV CI job and that one crate *not* inheriting
`rust-version.workspace`. `targets` is deferred to slice 2.7, which owns
the `no_std` job and the choice of which bare-metal target proves it.

### 6.2 — Copyright holder and remote (§4 Q2)

**Decision.** Copyright line: `Copyright (c) 2026 Polytopic Lab`. Remote:
`https://github.com/Polytopic-Lab/lido.git`.

Both are recorded by the artifacts themselves — the `LICENSE` text and
the configured git remote — so neither goes in the decision log. The
remote is being created separately and is not on the critical path:
§3.2 steps 4–5 and all of §§3.3–3.6 run against a local repository, and
`git remote add` can follow whenever the URL exists.

The repository name pre-empts part of specs.md §16 Q1 (artifact naming).
Choosing one here does **not** close §16 Q1 — the crates.io *published*
names are settled in slice 10.1, and nothing in this slice should be read
as fixing them.

### 6.3 — Stub `main` (§4 Q3)

**Decision.** `fn main() {}` — silent, exit 0.

The crate is genuinely empty in this slice and nothing should read as a
promise about CLI behavior before slice 5.4 defines it. A "not
implemented" message on stderr with a non-zero exit is the friendlier
choice for a human who runs it by accident, but it invents an exit code
and a diagnostic string that specs.md does not define, and slice 5.4
would then have to either honor or silently change them. Slice-local;
not promoted.

### 6.4 — Test host: **`xtask`** (§4 Q4) → **D-002**

**Decision.** Option (b). A dedicated `xtask` crate hosts the
workspace-layout test, with `serde_json` as its dev-dependency for
parsing `cargo metadata` output.

This overrides the recommendation in §4 Q4 and §5 conflict 2, both of
which favored option (a). It is the deliberate choice: `xtask` is the
standard Rust home for project automation, and the workspace-layout check
is the first of what will be several such tasks — putting it in
`lido-cli/tests/` makes the product CLI the accidental owner of build
tooling, which gets harder to unwind with every task added.

### 6.9 — No PR for this slice (§4 Q9)

**Decision.** Neither option as posed. No branch, no PR: the documents
are brought into agreement first (§3.2 steps 1–2), then `git init`, then
the workspace is built directly on `main`. The loop — branch, plan, gate,
PR — starts at slice 0.2.

This reverses an earlier draft of this section, which called for a real
PR against a fresh remote. That draft was reasoning about a repository
that already existed. It does not. Both options in §4 Q9 presuppose a
`main` to open a PR *against*, and there is nothing to protect, nothing
to diff against, and no CI to run — a PR whose base commit is the empty
tree is a formality, not a review artifact. development.md §7 already
says this slice is "done by hand rather than through the loop"; taking
that at face value costs nothing and removes a fake gate.

**What is lost, and where it goes instead.** The PR body was carrying
four things (§4 Q9's real content). Each needs a home:

| Was going in the PR body | Now |
|---|---|
| Deliberate-failure check (§3.6) | Commit message of the commit adding the test |
| REQ-ARCH-040 added beyond plan.md's citation (§6.7) | §6.7 and §1's requirements table |
| `serde_json` license verification (§6.4 row 7) | §3.6's hygiene checks, by hand |
| design.md amendment (§6.4 row 1) | §2 "Modified", with its justification |

**Consequence.** Slice 0.1 gets no second pair of eyes, which is a real
cost — it is the slice that fixes the toolchain, the crate names, and the
tooling-crate precedent for everything after it. The mitigation is that
§6 exists and is committed: the decisions are reviewable in place, and
any of them can be revisited in slice 0.2, which *does* run the loop.
