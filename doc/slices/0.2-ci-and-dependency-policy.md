# Slice 0.2 — CI and dependency policy

> Historical implementation plan, not normative. See specs.md, design.md,
> code-style.md, and decisions.md for the documents of record.

**Plan DoD** (from plan.md, quoted verbatim):

> CI is green on all three platforms. A deliberately added copyleft
> dependency fails `cargo deny check` in CI, and the failure is
> demonstrated before being reverted. The reference runner specification is
> recorded in `doc/decisions.md`.

**Scope** (from plan.md, quoted verbatim):

> CI running build, `cargo test`, `cargo clippy -- -D warnings`, and
> `cargo fmt --check` on Linux, macOS, and Windows. `cargo-deny`
> license/advisory gate enforcing the permissive-only policy. Record the
> reference CI runner configuration that the compiler-throughput bar will
> later be measured against. Branch protection on `main` requiring all
> checks.

This is the first slice to run the full loop from development.md §2 —
branch, plan, human gate, PR, review. Slice 0.1 ran outside it (0.1 plan
§6.9) because there was no `main` to branch from and no CI to fail
against. This slice builds the thing it is the first to be judged by.

## 3. Tests first

CI is infrastructure, so "the test" is the gate itself and the thing that
must fail first is the gate, not a `#[test]`. The order below is chosen so
that each step has something observable to check.

### 3.1 Before the change

- `.github/workflows/` does not exist. Pushing a branch or opening a PR runs nothing; there is no signal to be green or red.
- `cargo deny check` fails locally with `no such command: deny` — the tool is not installed and no `deny.toml` exists.
- `main` is unprotected: a direct push, or a merge of a PR with no checks at all, succeeds.
- `doc/decisions.md` ends at D-004. No runner configuration is recorded anywhere, so slice 9.6 would have nothing to measure against.

All three DoD clauses fail: there is no CI to be green, no gate to fail
closed, and no recorded runner.

### 3.2 Step 1 — branch and commit the plan

Per development.md §2, branch `slice/0.2-ci-and-dependency-policy` off
`main`, and commit this file unchanged as the first commit. Branch
protection is applied at the *end* of this slice (§3.5), so the branch is
created while `main` is still unprotected — which is fine, and is the last
time it will be true.

### 3.3 Step 2 — the workflow, failing first

Add `.github/workflows/ci.yml` and push. The intended job structure:

| Job | Runs on | Steps |
|---|---|---|
| `test` | matrix: Linux, macOS, Windows | `cargo build --workspace`, `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings` |
| `fmt` | Linux only | `cargo fmt --all --check` |
| `deny` | Linux only | `cargo deny check` (scope per §4 Q3) |
| `runner-spec` | matrix: Linux, macOS, Windows | Prints the runner image label, arch, core count, memory, and `rustc -Vv`. Produces the REQ-NFR-010 artifact. |

`fmt` and `deny` are single-platform by construction: `rustfmt`'s output
is platform-independent given a pinned toolchain (D-001), and a license
tree is a property of `Cargo.lock`, not of the host. `clippy` stays in the
matrix because it is the check most likely to diverge once `cfg`-gated
code exists.

**Expect the first run to be red**, and treat a first-try green as a
reason to look harder — it usually means the workflow did not trigger.
Failures to expect and fix here: `cargo deny` not installed before the
`deny` job runs it, Windows shell quoting in the `runner-spec` step, and
the toolchain action disagreeing with `rust-toolchain.toml`.

Iterate until all four jobs are green on all three platforms. That is DoD
clause 1.

### 3.4 Step 3 — the deliberate failure (DoD clause 2)

The `deny` job passing over a tree that contains no copyleft proves only
that the job runs. The DoD asks for the gate to be shown to fail closed,
which is the actual content of REQ-DEP-020's coverage.

1. On this slice's branch, add a GPL- or AGPL-licensed crate as a dependency of `xtask` — chosen and license-verified at implementation time (§4 Q6), not named here.
2. Push. **The `deny` job must fail**, and the failure message must name the crate and the rejected license — not merely exit non-zero.
3. Record the failing run's URL. It is the evidence for DoD clause 2 and goes in the PR body.
4. Revert the commit. Confirm `deny` is green again.

Both commits stay in the branch history, so the demonstration is
reproducible from the merged PR rather than asserted in prose. This is the
same shape as slice 0.1 §3.6's deliberate-failure check, promoted to a
required DoD clause because here the thing being tested *is* the gate.

Also confirm the inverse — that the gate is not merely rejecting
everything — by checking the green run enumerated the real dependency
tree. §4 Q4 lists what is in it today.

### 3.5 Step 4 — branch protection (ordering matters)

Applied **after** §3.3 is green, not before: GitHub's required-status-check
picker only offers check names it has already observed, so protecting
`main` first means naming checks by hand and getting them subtly wrong.

Settings per §4 Q8. Once applied, verify by attempting a direct push to
`main` and confirming it is rejected.

### 3.6 Step 5 — record the runner (DoD clause 3)

Take the `runner-spec` job's output from a real run on the merge commit's
CI and paste it verbatim into **D-005**, along with the run URL and date.
Verbatim matters: a paraphrased core count is exactly the kind of detail
that turns slice 9.6's measurement into an argument.

### 3.7 After the change

- Every PR against `main` runs four jobs; all are required; none can be merged around.
- `cargo deny check` passes locally and in CI over the current tree.
- The copyleft canary's failing run is linked from the PR body, and its revert is in the branch history.
- `doc/decisions.md` carries D-005 and D-006.
- A direct push to `main` is rejected.

Local pre-push hygiene, unchanged from slice 0.1 §3.6: `cargo fmt --check`
and `cargo clippy -- -D warnings` clean before pushing, so CI is
confirming rather than discovering.

## 4. Open questions for review

Nine. Q1–Q4 and Q8 shape artifacts that later slices inherit; Q5–Q7 and Q9
are local. Recommendations are given, but none is decided here. See A1-A9 
for answers.

**Q1 — Pin runner images, or track `-latest`?**
`ubuntu-latest` silently rotates to a new image; the whole point of D-001
was that `rustfmt` and `clippy` output must not drift underneath us, and
REQ-NFR-010 asks for a runner configuration that makes a timing figure
*reproducible*. Both arguments point the same way. **Recommend pinned
labels** (e.g. `ubuntu-24.04`, `windows-2025`, and a pinned macOS label),
with the consequence recorded in D-006: pinned images are eventually
deprecated and removed by GitHub, so an image bump becomes its own PR —
the same deal D-001 made for the toolchain. Against: that is a recurring
maintenance interrupt on a project with one contributor.

**A1 - Pin runner images.**
Pin the runner images to ubuntu-24.04, windows-2025, and macos-26.

**Q2 — What exactly goes in the reference-runner record, and which OS is "the" reference?**
REQ-NFR-010 says "the project's reference CI runner configuration",
singular, but the matrix has three. **Recommend Linux as the reference**
(cheapest, fastest, the platform CI will always have) and that D-005
record: runner image label, arch, core count, available memory, `rustc
-Vv`, the cargo profile the future measurement will use (**recommend
`--release`** — a debug-build timing would be meaningless against a 5s
bar), and whether the figure assumes a warm dependency cache. The last two
are the ones slice 9.6 will otherwise have to invent. Should D-005 also
record the *other* two platforms' specs as informative context?

**A2 - Use Linux as the reference runner.**
Do not use Windows or macOS for reference**

**Q3 — `cargo deny` scope on PRs: all four checks, or split advisories out?**
plan.md's scope says "license/advisory gate", so advisories are in scope
for the slice — the question is only *where they run*. `licenses`, `bans`,
and `sources` are pure functions of `Cargo.lock` and are stable. The
`advisories` database is not: an advisory published overnight turns the
next unrelated PR red, and DoD clause 1 ("CI is green") then depends on
the outside world. **Recommend `licenses`/`bans`/`sources` as the required
PR check and `advisories` on a daily schedule** (`.github/workflows/audit.yml`),
which still gates the project on advisories but as its own signal. Note
this makes the required-check set differ from development.md §3.5's
unqualified `cargo deny check` — see §5 conflict 2. The alternative is one
job with everything, accepting the flakiness. Also: should `bans` include
`multiple-versions = "deny"`? It is good hygiene and currently vacuous
(§4 Q4's tree has no duplicates), but it will eventually fail on a
transitive diamond that is nobody's fault.

**A3 - Split advisory checks out**
Use Dependabot alerts to cover new advisory landings, and `cargo deny` to cover license and ban violations.
**Dependabot alerts: on.** Covers a new advisory landing against dependencies you haven't touched. No workflow, no minutes, fires on the database changing rather than on a timer. Verify it's actually enabled in the repo's Security settings rather than assuming — the docs say admins enable it, and I couldn't confirm it's on by default for public repos.
- **Dependabot version updates: off.** That's the one that opens PRs on a cadence; it would put back the noise you're removing.
- **`cargo deny check licenses bans sources`** — required check, every PR. This is the REQ-DEP-020 gate and the only part that must be required.
- **`cargo deny check advisories`** — same workflow, separate job, `paths:`-filtered to `Cargo.lock`, `Cargo.toml`, `**/Cargo.toml`, `deny.toml`, plus `workflow_dispatch`. Not a required check, since a path-filtered job that doesn't run reports nothing, and a required check that never reports blocks the PR forever — the §3.5 trap.

**Q4 — Is `Unicode-3.0` acceptable under REQ-DEP-020?**
This one blocks a green build, so it needs an answer. The current
dependency tree, from `cargo metadata` on the committed `Cargo.lock`:

| Crate | License |
|---|---|
| `itoa`, `proc-macro2`, `quote`, `serde`, `serde_core`, `serde_derive`, `serde_json`, `syn` | `MIT OR Apache-2.0` |
| `memchr` | `Unlicense OR MIT` |
| `zmij` | `MIT` |
| `unicode-ident` | `(MIT OR Apache-2.0) AND Unicode-3.0` |

Every crate but the last is trivially satisfied by putting `MIT` and
`Apache-2.0` in the allow-list. `unicode-ident` is joined by **AND**, so
`Unicode-3.0` must be allowed explicitly or `cargo deny check licenses`
fails on the tree as it stands today. REQ-DEP-020 requires "OSI-approved
permissive … compatible with MIT redistribution" and names five licenses
"e.g.", so the list is illustrative rather than closed. Unicode-3.0 is
permissive and non-copyleft. **Recommend allowing it**, with a comment in
`deny.toml` naming `unicode-ident` as the crate that forced it. Flagging
rather than deciding because it is an interpretation of a requirement, and
because whatever list is written here is the one every future dependency
is judged against. Should `Unlicense` also be allowed (not needed —
`memchr`'s `OR MIT` branch satisfies), and should `BSD-2-Clause`,
`BSD-3-Clause`, `BSL-1.0`, and `ISC` be pre-allowed on the strength of
REQ-DEP-020's own list, or added only when a real dependency needs them?
**Recommend pre-allowing exactly REQ-DEP-020's five**, so the file traces
to the requirement, plus `Unicode-3.0` with its comment.

**A4 - Allow Unicode-3.0**
Allow Unicode-3.0 with a corresponding comment in deny.toml. Keep the allowed list to REQ-DEP-020's five plus Unicode-3.0.

**Q5 — How is `cargo-deny` obtained in CI?**
`EmbarkStudios/cargo-deny-action` (fast, but a third-party action in the
gate) versus `cargo install cargo-deny --locked` (slow — minutes of
compile on every run — but no new trust dependency). **Recommend the
action, pinned by commit SHA** rather than by tag, and the same policy for
every other third-party action used. A tag is mutable; the gate that
"can't be talked around" (development.md §3.5) should not be reachable by
someone who can move a tag.

**A5 - Use the action, pinned by commit SHA**

**Q6 — Which crate is the copyleft canary, and does it go on this branch?**
The canary must be a real crates.io package with a GPL-family license, and
its license must be verified at the moment it is added rather than assumed
from memory — so this plan deliberately does not name one. On placement:
**recommend a commit on this slice's branch, reverted in the next commit**,
which is what the DoD's "demonstrated before being reverted" describes and
leaves the evidence in the merged history. The alternative — a throwaway
branch and PR, never merged — keeps this PR's history clean but puts the
evidence somewhere that can be deleted. Which do you want?

**A6 - Use a commit this slice's branch, reverted in the next commit**
Use `synfx-dsp` 0.5.6, `GPL-3.0-or-later` as the canary.

**Q7 — Add the REQ-CLI-090 smoke test, or leave the matrix as the only coverage?**
A test that runs the built binary and asserts exit 0 is the only thing
that would make the three-platform matrix assert something about the *CLI*
rather than about the workspace. It is also nearly vacuous today, since
`main` is `fn main() {}` (0.1 plan §6.3) — it can only catch a binary that
fails to link or launch. **Weak recommendation to include it**, on slice
0.1 §6.7's precedent (add the mechanical guard before there is anything to
catch), recorded here because plan.md's scope for 0.2 does not mention
tests. Against: it is the only change this slice would make inside a
product crate, and slice 6.8 owns the real version.

**A7 - Skipl the smoke test.**

**Q8 — Branch protection settings.**
Four sub-decisions, and one has a trap in it:
- *Required checks:* every job from §3.3. Note that a matrix job appears once per leg, so the list names each OS variant separately.
- *Require a PR before merging:* yes.
- *Required approvals:* **recommend 0.** GitHub does not let you approve your own PR, so any non-zero number hard-blocks a solo maintainer. The human gate in development.md §2 is a review of the *plan*, before implementation, and does not depend on GitHub's approval mechanic.
- *Include administrators:* **recommend yes**, since "the gate that can't be talked around" is the entire point — but it means a broken `main` cannot be fixed by force-push, only by another PR. Your call, and easy to reverse.
- *Linear history / require branches up to date:* recommend requiring linear history; requiring branches be up to date is friction that only pays off with concurrent contributors.

**A8 - User required checks, 0 approvals, include administrators, and linear history.**

**Q9 — Version bump and the README badge.**
Per **D-004**, the versioned surface is the public Rust API, the CLI
interface, generated code, and the wire format. CI configuration is none
of those, so **recommend no version bump and no tag** for this slice — the
PR template's semver line reads "none". Confirming because D-004 makes
that an explicit judgement rather than an omission. Separately: add a CI
badge to `README.md`, or leave the README untouched?

**A9 - Do not version bump and do not tag this slice.**

## 5. Spec conflicts found

Two, neither blocking, neither requiring a change to `specs.md`,
`design.md`, or `code-style.md` in this PR.

1. **design.md §2's tree does not admit `.github/` or `deny.toml`.** The
   layout tree shows `Cargo.toml`, `crates/`, `runtime/`, `xtask/`,
   `conformance/`, and `doc/`. It already omits

   Nothing is *violated*: §2's prose scopes the tree to the Rust workspace
   and its documents, and no numbered requirement asserts the tree is
   exhaustive. Slice 0.1 §5 conflict 1 already proposed a docs PR at Phase
   0 close to refresh §2; **this slice should not touch design.md**, and
   the Phase 0 close docs PR should now cover `.github/` and `deny.toml`
   as well as the `doc/` tree.

2. **development.md §3.5 lists `cargo deny check` unqualified as a
   required check**, which reads as all four sub-checks on every PR. If
   §4 Q3 splits `advisories` onto a schedule, the required-check set will
   not match that list. development.md is explicitly *not* normative
   (CLAUDE.md's document list; development.md §0), so this is a process
   document drifting from practice rather than a spec violation — but it
   is the document a future session will read to learn what CI requires.
   Recommend the same Phase 0 close docs PR amend §3.5 to match whatever
   Q3 decides. Recording it here so it is not rediscovered as a surprise
   in Phase 2.

Two further notes that are not conflicts:

- **REQ-NFR-010 is only one-third addressed.** This slice records the
  runner; slice 9.6 measures against it; the 200-type schema that the
