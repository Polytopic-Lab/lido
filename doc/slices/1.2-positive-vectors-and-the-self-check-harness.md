# Slice 1.2 — Positive vectors and the self-check harness

> Historical implementation plan, not normative. See specs.md, design.md,
> code-style.md, and decisions.md for the documents of record.

**Plan DoD** (from plan.md, quoted verbatim):

> The self-check re-derives every expected CBOR and JSON vector with the
> independent implementation and passes in CI **with zero Lido code
> involved**. Mutating any expected byte causes the self-check to fail.

**Scope** (from plan.md, quoted verbatim):

> Author positive vectors for every schema and verify them with an
> independent tool (e.g. Python `cbor2` plus a canonical-CBOR checker),
> asserting RFC 8949 §4.2 conformance including key order. Build the
> corpus self-check script and wire it into CI.

Slice 1.1 built the frame; this slice puts the oracle's first real content
in it and gives the frame teeth. Everything about the layout, manifest
format, value model, and tooling was settled in **D-007** and **D-008**
and is not reopened here. What is new is (a) ~75 positive cases, (b) the
three-way verification D-007 §4 specified, (c) a mutation test that proves
the verification can fail, and (d) promotion of the `conformance` job to a
required check.

**Two spec gaps must be closed by a docs PR before this slice can be
implemented** (§5 Q1, Q2 — answered: that PR comes first): specs.md does not define the JSON text of a
floating-point number or the escaping of a JSON string. Both are needed for
byte-exact `json` vectors. This is the same shape as REQ-RT-175/177 at the
1.1 kickoff and the same remedy applies. The rest of this plan is written
so that it holds whichever way those two answers go; only the float and
string vectors' `json` fields wait on them.

## 3. Verification design and tests first

### 3.1 The three-way check (D-007 §4), per case

1. `cbor2.loads(cbor)` equals the declared `value` (type-strict: a Python
   `True` is not `1`, `1.0` is not `1`, NaN equals NaN, map pairs compared
   **in order**, trailing bytes are an error).
2. `cbor2.dumps(loads(cbor), canonical=True) == cbor`.
3. `cborcheck.check(cbor)` returns no violations.

`json` is re-derived from `value` by a small Python writer built on the
stdlib `json` module (independent lineage again): `uint`/`int` beyond
±(2^53−1) → JSON string (REQ-RT-220); `bstr` → base64url, no padding
(REQ-RT-200); `map` → object with members in wire order (REQ-RT-177), uint
keys as decimal names (REQ-KEY-030); enumerations and choices need no
special case because the value model already expresses them; separators
`(",", ":")` (REQ-RT-175). Float and string text follow whatever Q1/Q2
decide, and `ensure_ascii=False` plus stdlib float `repr` are only used if
they match that decision. The result is compared to `json` as exact text.

(3) is not redundant with (1)+(2) and the plan shows it: with `cborcheck`
disabled, the mutation test of §3.3 must report survivors (a non-shortest
head decodes to the same value; cbor2 canonical mode is only asked about a
re-encode). That demonstration is in the PR body.

If `cbor2`'s canonical mode and `cborcheck` ever disagree, the RFC decides,
the disagreement is reported rather than papered over, and the vector is
not weakened to make either pass.

### 3.3 The mutation test (DoD clause 2)

"Mutating any expected byte causes the self-check to fail" is made a
test rather than a claim. For every case and every byte position of
`cbor`, substitute each of the other 255 values; the full per-case check
must then report ≥1 violation (cbor2 decode error, value mismatch,
re-encode mismatch, or `cborcheck` violation). For `json`, every
character position is substituted with a fixed probe set and
deleted/duplicated once; exact text comparison must fail. Any mutation the
checker accepts is a **survivor**, printed with its case id, offset, and
byte, and the mode exits non-zero.

Cost: ~75 cases × ~40 bytes × 255 ≈ 760k checks. Expected under a minute
in CI; **measured in the PR**. If it exceeds ~2 minutes the fallback is the
8 single-bit flips per byte plus all 255 values only for head bytes, with
the reduction stated in the PR body — not silently.

Only `cbor` and `json` are mutated. Mutating `value`, `root`, or metadata
fails or passes for reasons that are not the DoD's.

## 5. Open questions — raised, and how they were answered

Each is a place where the specs do not determine the answer. None is
decided here. Recommendations are marked.

**Q1 — What is the JSON text of a floating-point number? (spec gap;
blocks the float vectors' `json`.)** specs.md says NaN/∞ are errors
(REQ-RT-210) and that wide integers become strings (REQ-RT-220) but is
silent on how `1.5`, `100000.0`, `1e300`, `5.960464477539063e-8`, `-0.0`,
or a `float32` value are *written*. Byte-exact comparison across three
languages needs one rule; the default float printers differ (Java
`Double.toString` writes `1.0E300`, Python writes `1e+300`, JavaScript
`1e+300`, C++ depends on the library). Sub-questions: does an integral
float write `1.0` or `1`; which exponent form; are `float32` values
printed as the shortest string that round-trips *as a float32* (so
`3.4028235e+38`) or as the double expansion; and which NaN CBOR forms are
canonical (REQ-RT-160 says "shortest that round-trips", which does not fix
sign or payload — only `f97e00` would be vectorised). **Recommendation:** a
docs PR adds a requirement in §9.1 before this slice's implementation,
exactly as REQ-RT-175/177 were added before 1.1's. Until then the plan's
float vectors cannot be finalised. Alternative: restrict float vectors to
values with exactly one reasonable spelling — rejected, because that avoids
the rule rather than testing it, and the first backend to disagree would
"fix" the corpus.

> **Answered: as recommended — a docs PR first, merged before this slice is implemented.** It adds a requirement to specs.md §9.1 fixing the JSON text of float values (integral-float form, exponent form, `float32` printed as the shortest string that round-trips as a float32) and the canonical NaN CBOR form. Its exact wording is that PR's business; this slice's float `json` vectors are authored against it. Implementation does not start until it has merged.

**Q2 — How is a JSON string escaped? (spec gap.)** RFC 8259 permits `é`
or a raw `é`, `\/` or `/`, upper- or lower-case hex. REQ-RT-175 fixes
whitespace but not escaping. **Recommendation:** same docs PR: escape only
`"`, `\`, and U+0000–U+001F (short forms `\b \f \n \r \t`, otherwise
`\u00xx` lowercase); everything else, including all non-ASCII, raw UTF-8.
This is what Python `json.dumps(ensure_ascii=False)` already does, which
keeps the independent writer trivial.

> **Answered: as recommended.** The same docs PR as Q1 fixes string escaping: only `"`, `\`, and U+0000–U+001F are escaped (short forms `\b \f \n \r \t`, otherwise lowercase `\u00xx`); all other characters, including non-ASCII, are raw UTF-8.

**Q3 — Do JSON *encode-error* positive vectors belong in this slice?**
`Edge` with NaN or ∞ is valid CBOR (`f97e00`, `f97c00`) whose JSON
encoding must raise (REQ-RT-210). The positive record requires a `json`
string. Options: (a) add an optional `json_error` member and make `json`
and `json_error` mutually exclusive — a schema change, additive,
`manifest_version` stays 1 unless you say a new optional member is a
version bump (D-007's Consequences make that your call); (b) defer to 1.3
which defines the error-vector records anyway. **Recommendation:** (b).
The CBOR half of those cases is not lost — it is just not authored yet.

> **Answered: (b), as recommended.** Deferred to 1.3, which defines the error-vector records. `manifest.schema.json` is not touched by this slice.

**Q4 — Where do decode-only vectors live?** REQ-RT-080 (absent field →
default), REQ-RT-200/220/175 (alternate JSON spellings) describe inputs
that decode to the right value but are not the canonical output. They are
neither positive-roundtrip nor negative. 1.3's `noncanonical` kind is the
nearest fit, but 1.3's requirement list (plan.md) names none of these four,
and 1.4's DoD ("every requirement in §9.1–§9.8 maps to a case") will fail
on REQ-RT-200/220/175 unless something owns them. **Recommendation:**
leave to 1.3's plan, and flag now so the 1.3 plan.md entry gains the IDs.
This is a plan.md edit (a working document), not a spec edit.

> **Answered: as recommended.** Left to 1.3's plan. plan.md's 1.3 requirement list gains REQ-RT-080, REQ-RT-175 (decode half), REQ-RT-200 (decode half) and REQ-RT-220 (decode half) in a plan.md edit (a working document), made with the 1.3 plan, not here.

**Q5 — Encode-error vectors generally** (REQ-RT-250 out-of-range,
REQ-RT-255 non-half `float16`, REQ-RT-210). Same record-shape question as
Q3/Q4. **Recommendation:** defer all three to 1.3; one shape decision for
all of them is better than three.

> **Answered: as recommended.** REQ-RT-210, 250 and 255 error vectors are deferred to 1.3, with one record-shape decision for all of them.

**Q6 — Schema changes.** `Counters` has keys 1 and 2, so the
`"9"`-before-`"10"` JSON ordering trap that REQ-RT-177 calls out cannot be
vectorised without a schema with keys ≥ 10. `Header` has 1, 2, 9 — also no
two-digit key. Editing an existing schema is not forbidden (schemas are not
vectors), but 1.1 is merged and `construct-coverage.json` cites them.
Options: (a) add a second struct `Wide = {2: …, 10: …, 9: …}` to
`json_edge.cddl` (no construct-coverage change; the check only needs the
file); (b) a new schema file (touches `index.json` and 1.1's
"sixteen"). **Recommendation:** (a). It is the one place the JSON order
rule can be got wrong in all three languages at once.

> **Answered: (a), as recommended.** `json_edge.cddl` gains `Wide = { 2: uint, 10: uint, 9: uint }` (plus the vectors that use it). `construct-coverage.json` is unchanged. This adds `json_edge.cddl` to this slice's *Modified* list.

**Q7 — Is `value`-vs-`root` validity checked?** D-007 §3 rejected a Python
CDDL parser, so nothing verifies that a case's `value` is a valid instance
of its `root` type; a mistake there would be caught only by a human reading
the diff, or in Phase 3 when the real parser can validate the corpus.
Check 9 narrows the gap (root must exist) but does not close it.
**Recommendation:** accept for this slice, and record in the PR body that
the first Phase 3 slice with a validator should add "every positive case's
`value` validates against its `root`" as a corpus-wide check (that check
would use Lido code, so it lives in `crates/`, not in `conformance/tools/`,
and cannot be part of the zero-Lido-code gate).

> **Answered: accept, as recommended.** The PR body records that the first Phase 3 slice with a validator should add "every positive case's `value` validates against its `root`" as a check under `crates/`, outside the zero-Lido-code gate.

**Q8 — Promoting `conformance` to a required check.** D-007 and
development.md §3.5 say it becomes required at this slice. Branch
protection is edited in GitHub by hand, only after the job has run once
(a status check cannot be required before it has reported), and D-006's
list is append-only so the change needs a **D-009**. Ordering problem: the
PR cannot truthfully say "now required" before you have done it.
**Recommendation:** the PR includes D-009 stating the job is required
*as of merge*, the PR body lists the exact branch-protection edit
(add `conformance` to required checks, not strict), and you do it between
approval and merge. If you would rather record it after the fact, D-009
moves to a follow-up docs PR — say which.

> **Answered: as recommended.** The PR includes D-009 (`conformance` required as of merge) and lists the exact branch-protection edit (add `conformance`, not strict). The human makes that edit between approval and merge.

## 6. Spec conflicts found

No part of this slice requires editing `specs.md`, `design.md`, or
`code-style.md` **if Q1 and Q2 are resolved first by a separate docs PR**
(§5 Q1, Q2 are gaps, not contradictions). If they are not, the float and
string vectors must wait; the other ~55 vectors are unaffected and could
land first. If you want that split, it is a smaller 1.2 plus a new slice,
and the plan.md edit is yours.

Noted, not a conflict: specs.md §9.1 REQ-RT-160 says floats use the
"shortest form that round-trips" independent of declared width, while
REQ-GEN-140 says a `float16` field "emits the half-precision form". The two
agree only because REQ-RT-255 forbids `float16` fields holding
non-half-representable values (the spec says so itself). The
`primitives/float_width_independent` vector exists to pin exactly that
reading: it asserts a `float64` field holding 1.5 encodes as `f93e00`. If
that is not what you intend, say so before authoring.

## 7. DoD mapping

| DoD clause | Satisfied by |
|---|---|
| "re-derives every expected CBOR and JSON vector with the independent implementation" | checks 10, 11 — `cbor2`, `cborcheck.py`, stdlib `json`, no Lido code |
| "passes in CI" | `conformance` job runs `--check-format`, `--self-test`, `--mutation-test` |
| "with zero Lido code involved" | the job installs only `requirements.txt` and runs Python; no `cargo`, `rustup`, or `target/` reference. Verified by reading the job, and shown by the job's log in the PR. |
| "Mutating any expected byte causes the self-check to fail" | check 13; plus the PR body demonstrating survivors when `cborcheck` is disabled and none when enabled |

**Semver impact: none** (D-004 §2): no crate API, CLI, generated code, or
wire format. The corpus constrains the wire format but does not define it.
