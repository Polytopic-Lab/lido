# Slice 1.4 — Evolution pairs and the coverage manifest

> Historical implementation plan, not normative. See specs.md, design.md,
> code-style.md, and decisions.md for the documents of record.

**Plan DoD** (from plan.md, quoted verbatim):

> Every requirement in specs.md §9.1–§9.8 maps to at least one corpus case
> in the coverage manifest, and CI fails if a requirement has no case. Every
> §9.6 compatibility scenario has an old/new schema pair.

**Phase DoD** (from plan.md, quoted verbatim, because this slice closes
Phase 1):

> The corpus self-check passes in CI with zero Lido code, and the coverage
> manifest shows full requirement coverage across §9.1–§9.8.

**Scope** (from plan.md, quoted verbatim):

> Author schema-evolution pairs (old/new revisions) for the §9.6
> compatibility matrix. Complete the coverage manifest mapping requirements
> to cases, and make its completeness a CI check.
>
> **Requirements.** REQ-COMPAT-010/020/060; specs.md §9.1–§9.8.

Slices 1.1–1.3 built and filled the oracle's positive, negative, and
non-canonical halves. This slice adds the last kind (`evolution`), and then
turns "is the oracle complete?" from a belief into a CI check.

**The DoD cannot be met literally.** Of the 61 requirements in specs.md §9,
27 have no case today, and 16 of those can never have one: they are API
shape (REQ-RT-090/095/097/098/100), build constraints (REQ-RT-110–150),
optional behaviour (REQ-RT-260, 280), configuration (REQ-RT-270/290), and
explicit non-guarantees (REQ-COMPAT-040/050). A byte-exact vector cannot
test "the Rust core is `no_std`". §5 Q1 asks for plan.md's DoD to be amended
so that a recorded, checked *exemption* counts. The other 11 are coverable,
and this slice covers them.

## 3. The §9.6 compatibility matrix and the pairs

specs.md §9.6 does not draw a table; it states guarantees (REQ-COMPAT-010,
020, 025, 030, 035, 060) and non-guarantees (040, 050). "The §9.6
compatibility matrix" is taken to be *scenario × direction*, where a
scenario is a way a schema grows that the spec says is safe. The seven
scenarios (Q6 asks you to confirm the list):

| Pair (`schemas/evolution/…`) | v1 → v2 | Scenario enum | REQ |
|---|---|---|---|
| `add_optional_field` | `Person {name, age}` → `+ ? email: tstr` | `add_optional_field` | 010, 020, 025 |
| `add_defaulted_field` | `Settings {name}` → `+ ? retries: uint .default 3` | `add_defaulted_field` | 010 (default populated), 020, 190 |
| `add_uint_keyed_field` | `Header {1: int, 2: bstr}` → `+ ? 3: tstr` | `add_uint_keyed_field` | 010, 020, 035, KEY-030 |
| `append_array_element` | `Triple [uint, tstr]` → `[uint, tstr, ? bool]` | `append_array_element` | 060, 010 |
| `field_declared_first` | `Account {id, balance}` → `{? nickname: tstr, id, balance}` | `declaration_order_independent` | 030, KEY-050, RT-165 |
| `nested_struct_gains_field` | `Order {id, items: [* Item {sku}]}` → `Item` gains `? note` | `nested_struct_gains_field` | 020 (skip inside arrays) |
| `unknown_value_types` | `Probe {id}` → `+ ? blob, ? ratio, ? flag, ? nothing, ? tags, ? point, ? scores` | `unknown_value_types` | 020 (skip any value) |

The last is the one that earns its keep: `skip_value()` (design.md §4.5)
must discard an unrecognized value *without knowing its type*, so its
vectors put a `bstr`, a float, a bool, a `null`, an array, a nested map and a
table in the unknown position, one case each plus one with all seven.

Per pair, cases are authored **in both directions** and, where the spec says
"CBOR or JSON", in both encodings: ≈ 36 cases in total. A `new_to_old` case
has the new writer's canonical bytes as `input` and the old reader's value
as `value`; an `old_to_new` case has the old writer's canonical bytes and the
new reader's value, with defaults populated.

There are no vectors for REQ-COMPAT-040 (removing, renaming, type change,
optional→required, key reuse, array insert/reorder, variant changes: the spec
says Lido does not guarantee them), REQ-COMPAT-050 (tables: no concern), or
the *unsafe* half of REQ-COMPAT-035 (key reuse "SHALL be documented as
unsafe": a user-documentation duty, owned by the documentation slice).

## 4. The record, the verification, and the coverage rules

### 4.1 The `evolution` record

Envelope: `"kind": "evolution"` and `"pair": "<name>"` **in place of**
`"schema"`; the schema revisions are
`schemas/evolution/<name>/v1.cddl` and `v2.cddl`. Case:

```json
{ "id": "add_optional_field/new_writer_old_reader_email",
  "root": "Person", "description": "…", "requirements": ["REQ-COMPAT-020", "REQ-COMPAT-025"],
  "derivation": "cbor2",
  "scenario": "add_optional_field",
  "direction": "new_to_old",
  "input": { "cbor": "a3…" },
  "ignored": ["email"],
  "value": { "map": [ … ] },
  "cbor": "a2…", "json": "{\"age\":36,\"name\":\"Ada\"}" }
```

`value`, `cbor`, `json` are the **reader's** canonical vector (so, for
`new_to_old`, what the old code decodes *and would re-emit*: REQ-COMPAT-025).
`ignored` lists (REQ-RT-066 paths) the input entries the reader must discard;
for `old_to_new`, `populated` lists the value entries the reader fills in.

### 4.2 What the self-check confirms

For every evolution case:

1. `value`, `cbor`, `json` pass the 1.2 three-way check: they are a valid
   positive vector for the *reader's* schema.
2. The `input` is well-formed and valid (`cborcheck.analyze`; strict JSON) and
   is the writer's **canonical** encoding: `cborcheck.check` is clean for CBOR,
   and for JSON the text equals the compact canonical form of the writer's
   value. A deterministic writer never emits anything else.
3. `new_to_old`: every pair of `value` occurs in the decoded `input`, and
   each `ignored` path resolves in `input` and does **not** resolve in `value`
   (the extras are really extras, and really dropped). `old_to_new`: every
   pair of `input` occurs in `value`, and each `populated` path resolves in
   `value` and not in `input`.
4. Both revisions exist, define `root`, and differ.

Per pair and across the corpus: every scenario enum value has ≥ 1 pair, and
the pair has ≥ 1 case in each direction it is meaningful for (all seven are
meaningful both ways; `append_array_element`'s `old_to_new` is "trailing
optional absent", its `new_to_old` is "extra element discarded").

### 4.3 The coverage manifest

`coverage.json`:

```json
{ "manifest_version": 1,
  "scope": "specs.md §9",
  "implied_by_kind": { "positive": ["REQ-RT-010", "REQ-RT-020", "REQ-RT-030", "REQ-RT-040", "REQ-RT-050", "REQ-RT-170"] },
  "requirements": {
    "REQ-RT-160": { "cases": [ "…" ] },
    "REQ-RT-110": { "exempt": { "category": "build_constraint", "reason": "…", "tested_in": "slice 2.7" } } } }
```

The checks:

- **Completeness against the spec.** The set of requirement ids is parsed from
  specs.md §9 itself (bullets of the form `- **REQ-…**` between `## 9.` and
  `## 10.`), as `check_coverage` already does for §3. A requirement added to
  §9 with no case and no exemption fails CI, which is the DoD's "CI fails if a
  requirement has no case". A requirement in `coverage.json` that is not in
  §9 also fails.
- **Freshness.** `coverage.json`'s `cases` are *derived*: each case id appears
  under every id in its own `requirements`, plus every requirement implied by
  its kind. `--write-coverage` writes the file; the default run recomputes it
  and fails on any difference, so the file cannot be hand-edited into a lie,
  and a case cannot be added or re-tagged without the manifest following.
- **Exemption discipline.** An exemption needs a `category` from a closed
  enum, a `reason`, and a `tested_in` naming a slice (`slice N.M`) that exists
  as a heading in plan.md. An exempt requirement that *also* has a case fails
  ("stale exemption"), so adding a vector later forces the exemption out.
- **Every id referenced is real**: case ids exist; requirement ids exist in
  specs.md (extends 1.2's check to the manifest).

| # | Check | Fails before | Passes after |

| 26 | `check_index`/`check_schemas_have_cases` are path-based; `v1.cddl` in two pairs does not collide; pair files are not required to have *positive* cases | seven pairs listed by name | updated |

## 5. Open questions — raised, and how they were answered

All nine were answered "as recommended"; each answer is recorded below the question.

**Q1 — The DoD says every §9.1–§9.8 requirement maps to a corpus case.
Sixteen cannot (see the table in §1).** Options: (a) amend plan.md's DoD to
"maps to at least one corpus case, or carries a recorded exemption naming the
slice that tests it, and CI fails if a requirement has neither"; (b) invent
vectors that "cover" `no_std` (dishonest); (c) leave the DoD and the CI check
unsatisfiable. **Recommendation: (a)**, as a small plan.md-only PR before
implementation (plan.md is a working document), so the DoD this slice is
judged against is the one it can meet. The Phase DoD's "full requirement
coverage" is read the same way.

> **Answered: (a), as recommended.** plan.md's 1.4 DoD and Phase DoD were amended by a plan.md-only PR (#11) before implementation. The DoD quoted at the top of this file is the wording at the time this plan was drafted; the amended wording is the one this slice is judged against. Implementation does not start until #11 has merged.

**Q2 — Which requirements are "§9.1–§9.8"?** Strictly the subsections, which
excludes REQ-RT-010–100 (they sit in §9's introduction, before §9.1).
**Recommendation: all of §9**, parsed from `## 9.` to `## 10.`. It is
stricter, it costs nothing (those requirements are API-shape and already
exempted or kind-implied), and it avoids a hole exactly where the runtime API
requirements live.

> **Answered: all of §9, as recommended** (`## 9.` to `## 10.`, including REQ-RT-010–100). The amended DoD says so.

**Q3 — How is `coverage.json` produced?** (a) generated from the cases'
`requirements` fields and committed, with a CI freshness check; (b)
hand-written, with a CI check that it agrees with the cases; (c) only
exemptions stored, case lists derived at check time. **Recommendation: (a).**
It is the literal "manifest maps requirements to cases" (D-007), harness
authors can read "which cases test REQ-X" without running Python, and a
generated file cannot be wrong by hand. The cost is size (every id under
every requirement; REQ-RT-160 alone lists every positive case) and a diff on
every future case. (c) is smaller and leaves no file to read.

> **Answered: (a), as recommended.** `coverage.json` is generated by `--write-coverage`, committed, and freshness-checked in CI.

**Q4 — Six requirements are exercised by every positive vector but tagged on
none** (REQ-RT-010/020/030/040 the four public codec entry points, 050 CBOR and
JSON agree, 170 byte-identical output). Tagging them means editing 88 existing
case records; those are expected-values files, and "never edit existing
vectors" is the safer reading even for metadata. **Recommendation:**
`coverage.json` carries `implied_by_kind` (above), applied by the generator, so
no existing case is edited. Only `positive` implies anything: a negative CBOR
vector exercises decode too, but claiming REQ-RT-020 from "an error was
raised" would overstate.

> **Answered: `implied_by_kind`, as recommended.** Only `positive` implies requirements; no existing case record is edited.

**Q5 — Confirm the 16 exemptions and the rule.** Categories:
`api_shape` (090, 095, 097, 098), `dependency_policy` (100),
`build_constraint` (110, 120, 130, 140, 150), `optional_behaviour` (260, 280),
`configuration` (270, 290), `non_guarantee` (COMPAT-040, 050). Each names its
testing slice (e.g. 110 → slice 2.7, 120 → Phase 8, 090/095/097 → Phase 2 API
slices, 270/290 → slice 2.1's limits API), checked against plan.md headings.
**Recommendation: as listed**, with the `tested_in` values verified against
plan.md during implementation; any I cannot place is reported, not guessed.
Specifically worth your eye: REQ-RT-270/290 were already deferred by D-010,
and REQ-RT-280 is a MAY about allocation that no input can observe.

> **Answered: as listed.** `tested_in` values are verified against plan.md headings during implementation; any that cannot be placed are reported rather than guessed.

**Q6 — Is the seven-scenario list the matrix?** It is derived from the
guarantees in §9.6 (§3 above). If you read the matrix as including the
non-guarantees (REQ-COMPAT-040's list: removing/renaming a field, type change,
...), those would be *negative* evolution scenarios whose expected outcome is
"unspecified", which a byte-exact oracle cannot state. **Recommendation:**
the seven guaranteed scenarios only; REQ-COMPAT-040 exempt (`non_guarantee`).

> **Answered: the seven guaranteed scenarios only, as recommended.** REQ-COMPAT-040 is exempt as `non_guarantee`.

**Q7 — Evolution record shape and `manifest_version`.** The `evolution` kind
was reserved by D-007, so no bump. Replacing the envelope's `schema` with
`pair` for that kind is an additive variant; same reasoning as D-010's
`encode_error`: no harness exists yet. **Recommendation:** as §4.1, recorded
in D-011, `manifest_version` stays 1. Say so if you read a changed envelope as
a version bump.

> **Answered: as recommended.** `pair` replaces `schema` in the `evolution` envelope; recorded in D-011; `manifest_version` stays 1.

**Q8 — Where does the coverage check run?** development.md §3.5 lists
"Requirement-coverage check" as its own required check. A separate job needs
another branch-protection edit by hand (D-006/D-009 note the list does not
update itself). **Recommendation:** run it inside the existing `conformance`
job, as the default `check_corpus.py` run, so it is already required, and
name it in D-011 so a failure is attributable. If you want the separate named
gate, say so: it is a one-job CI edit plus the protection edit.

> **Answered: inside the existing `conformance` job, as recommended.** No CI edit and no new branch-protection entry; D-011 names the check.

**Q9 — Accepting the verification gap for pairs.** Nothing here proves v2 is
a purely additive extension of v1, or that `value` is a valid instance of the
reader's schema: that needs a CDDL validator (1.2 Q7, 1.3 Q8). The checks in
§4.2 are structural: they prove the *direction* is right (extras really are
extra, defaults really are absent from the input). **Recommendation:**
accept, state it in the PR, and let the Phase 3 corpus-validates-against-schemas
check cover positives, negatives and evolution pairs together.

> **Answered: accept, as recommended.** Stated in the PR body; covered by the Phase 3 corpus-validates-against-schemas check.

## 6. Spec conflicts and gaps found

No edit to `specs.md`, `design.md`, or `code-style.md` is required. Noted:

- **No spec text** says what a decoder does with an unknown key *type*
  in a text-keyed struct (REQ-KEY-020 forbids mixing within a map type, so a
  conforming new writer never produces one); no vector.
- **REQ-COMPAT-020 and duplicate unknown keys**: REQ-RT-300 applies to the
  whole map, so a duplicated unknown key is an error; 1.3 already has the
  generic duplicate-key vectors, and none is added here.
- **REQ-COMPAT-020 with indefinite-length unknown values**: the new writer is
  canonical, so the vectors contain none; a *non-canonical* new writer is
  1.3's `noncanonical` territory and out of this matrix.
- plan.md's DoD wording: Q1.

Not found: any contradiction between §9.6 and §9.7 (`REQ-RT-320` omitting an
absent optional key is what makes `old_to_new` and `new_to_old` symmetrical
on the wire).
