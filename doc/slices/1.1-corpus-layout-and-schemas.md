# Slice 1.1 — Corpus layout and schemas

> Historical implementation plan, not normative. See specs.md, design.md,
> code-style.md, and decisions.md for the documents of record.

**Plan DoD** (from plan.md, quoted verbatim):

> The manifest format is documented and validates against its own schema.
> A construct-coverage list maps every construct in specs.md §3 to at
> least one corpus schema, and a script asserts the mapping is complete.

**Scope** (from plan.md, quoted verbatim):

> Define the corpus directory layout and the manifest format (schema +
> case name + value + expected CBOR hex + expected JSON), with a
> machine-readable manifest schema. Author CDDL schemas covering the full
> §3 subset: text- and integer-keyed structs, tables, fixed and
> homogeneous arrays, choices, enums, optionals, defaults, ranges,
> `bstr`, `float16`, nested and recursive types.

This slice builds the *frame* of the oracle, not the oracle. No expected
wire bytes are authored here beyond the single worked example that gives
`manifest.schema.json` something real to validate (§4 Q2) — that is slice
1.2. The thing being got right here is a format that three language
harnesses will read for the life of the project and a coverage check that
is tied to specs.md §3's actual text rather than to someone's memory of it.

The layout, manifest format, value model, and tooling choices this plan
implements were settled at Phase 1 kickoff and are recorded as **D-007**;
**D-008** settles whether integer-literal enumerations are in the §3
subset (they are). §4 below records the six questions this plan raised at
the human gate and how each was answered — all six are closed, and the two
with consequences beyond this slice were promoted into D-007 and D-008
before the plan was frozen. Where this plan and the decision log differ,
the log wins; this file is not normative.

## 1. Requirements covered

plan.md cites `REQ-ARCH-060` and "specs.md §3 in full".

### Cited by plan.md

| REQ | What it demands here | Where tested |
|---|---|---|
| **REQ-ARCH-060** — one language-independent fixture + vector suite, byte-exact, including non-canonical and malformed inputs | the `conformance/` tree, the manifest format, the index, and the `kind` taxonomy (`positive`/`negative`/`noncanonical`/`evolution`) that reserves slots for the non-canonical and malformed inputs REQ-ARCH-060 names | `conformance/tools/check_corpus.py::test_index_matches_tree` and `::test_every_case_file_validates`. The *content* of the suite is slices 1.2–1.4; this slice is tested on the frame being complete and self-consistent. |
| **specs.md §3** (the CDDL core subset) — every construct represented | one `.cddl` schema per construct group under `conformance/schemas/`, mapped in `construct-coverage.json` | `check_corpus.py::test_every_section_3_bullet_is_covered` — which parses §3 out of `specs.md` itself and fails if a bullet has no construct, or a construct has no schema, or a construct quotes text not present in §3 |

The §3 check is the DoD's "a script asserts the mapping is complete", and
it is deliberately stronger than a hand-maintained checklist: each entry in
`construct-coverage.json` carries the §3 bullet text it derives from, and
the script matches that text (whitespace-normalized) against `specs.md`.
A checklist drifts silently when §3 changes; this fails CI. It reads
`specs.md` and never writes it.

No requirement is *completed* by this slice. Slice 1.4's coverage manifest
should not mark any REQ as covered on the strength of this one.

## 2. Files

### Created — format and tooling

| Path | Purpose |
|---|---|
| `conformance/README.md` | The format documentation (DoD clause 1). Layout, the case-record fields, the value model's tag table, how to add a case, and the "never generated by Lido, never edited to make Lido pass" rule stated where an author will actually be standing. |

Envelope + the `positive` case record + the value model, fully. `negative`/`noncanonical`/`evolution` are declared as `kind` values whose records slices 1.3/1.4 fill in; until then the schema rejects them, so a case cannot be added in a shape nobody has reviewed. |

| `conformance/construct-coverage.json` | The §3 construct enumeration (§3 of this plan) with, per construct, its id, the §3 bullet text it derives from, and the schemas covering it. |
| `conformance/tools/check_corpus.py` | The self-check. At this slice: metaschema validation, index ⇔ tree, construct coverage vs `specs.md` §3, case-file validation, format check. Grows into the vector re-derivation harness in 1.2. |
| `conformance/tools/requirements.txt` | `cbor2` and `jsonschema` pinned to exact versions with hashes (D-007 §4). `cbor2` is unused at this slice and pinned anyway, so 1.2 does not also have to litigate the pin. |
| `.gitattributes` | `conformance/** text eol=lf` — a Windows checkout must not alter expected text. |

### Created — schemas (`conformance/schemas/`)

| File | Constructs | Notes |
|---|---|---|
| `primitives.cddl` | `bool` `int` `uint` `float16` `float32` `float64` `tstr` `bstr` `null` | One struct with one field per primitive, plus `null` as a standalone type alias (§8.1 maps it separately). |
| `struct_text_keys.cddl` | text-keyed struct, named type reference | Keys `age`/`name`/`email` — REQ-RT-165's own worked example, so canonical order and alphabetical order disagree. |
| `struct_uint_keys.cddl` | integer-keyed struct | COSE-style; non-contiguous keys (`1`, `2`, `9`) so numeric and declaration order disagree too. |
| `table_tstr.cddl` | table `{* tstr => int}`, `*` on table entries | |
| `table_uint.cddl` | table `{* uint => V}` with a struct value | Also exercises a table nested inside a struct. |
| `array_homogeneous.cddl` | `[* T]`, `*` on array elements | Both a primitive element type and a struct element type. |
| `array_fixed.cddl` | fixed-shape heterogeneous `[uint, tstr, bool]`, `?` on array elements | Trailing optional element is the REQ-COMPAT-060 fixture 1.3/1.4 will need. |
| `optional_default.cddl` | `?`, `.default`, `? f: T / null` | The last one is REQ-RT-330's presence-vs-nullability distinction, and the reason the value model separates absent from `{"null":null}`. |
| `choice.cddl` | choice over named types | Three named struct alternatives with *overlapping* optional fields — the ambiguity §9.8 exists to rule out. |
| `enum.cddl` | enumeration of literal values, both kinds | `Color = "red" / "green" / "blue"` and `Status = 10 / 20 / 30` (D-008). `Status`'s literals are deliberately neither `0,1,2…` nor contiguous, so that slice 1.2's vectors distinguish REQ-RT-385's "encode the literal" from "encode an ordinal index" — for integer enums the two otherwise coincide and the bug is invisible. |
| `ranges.cddl` | `x..y` on integer and on float | Includes `0..255`, which is REQ-RT-260's "range coincides with nothing the mapped type enforces" case under REQ-GEN-130. |
| `nested.cddl` | nested type references | Struct → struct → array of struct, three levels, so a decode error path like `order.items[3].price` (REQ-RT-065) has something to be produced from. |
| `forward_ref.cddl` | forward reference | A type used above its definition (REQ-CDDL-020). |
| `recursive.cddl` | recursive types | Two breakable shapes: `? next: Node` (optional edge) and `children: [* Tree]` (array edge) — the two indirection kinds REQ-CDDL-097 names. No unbreakable cycle: that is a rejection case (REQ-CDDL-095) and belongs to Phase 3. |
| `comments.cddl` | comments and whitespace per RFC 8610 §2 | Comments positioned to become doc comments under REQ-GEN-180. |
| `json_edge.cddl` | §9.2 representational edges | `bstr` (REQ-RT-200), `uint` above 2^53−1 (REQ-RT-220), a `float64` field whose vectors will include NaN/∞ encode-error cases (REQ-RT-210), integer keys (REQ-RT-230). |

Sixteen schemas. Each is small — the grouping is by construct, not by
realism, because a plausible-looking "order/customer/invoice" schema makes
it hard to say which construct a failure came from.

## 4. Open questions — raised, and how they were answered

Six questions went to the human gate. All six are closed below, and the
plan was frozen afterwards. Recorded here rather than deleted: the
questions are half the value of a plan, and a plan that shows only the
answers hides what was nearly decided differently.

**Q1 — Must the runtime's JSON writer emit compact JSON?** D-007 stores
each case's expected JSON as exact text in compact form, so byte-exact
comparison is possible. That imposes a constraint on the runtime
(REQ-RT-030) that specs.md §9.2 does not state. Options were: (a) keep it
and accept the corpus as the rule's home; (b) keep it and raise a docs PR
adding the rule to §9.2; (c) compare JSON semantically per harness,
costing byte-exactness and a parser per language.

> **Answered: (b), and done.** Compact form stands, and because a
> wire-visible rule does not belong in the corpus it is now in the spec:
> **REQ-RT-175** (no insignificant whitespace on encode, arbitrary
> whitespace accepted on decode) and **REQ-RT-177** (JSON member order is
> the canonical CBOR key order of REQ-RT-160/165), added to §9.1 by a
> kickoff docs PR that merged **before this branch existed**. REQ-RT-177
> was a second gap found while drafting the first — byte-exact JSON
> comparison needs a defined member order, and §9.1 had one only for CBOR.
> §9.1 rather than §9.2 because these are determinism rules, not
> "JSON cannot express this value" rules. **Neither edit is in this
> slice's diff**; specs are read-only during implementation
> (development.md §3.1).

**Q2 — Does this slice ship one worked positive vector?** For: the DoD's
"validates against its own schema" is hollow if the schema has no
instance, and a README example CI does not check is prose that rots.
Against: it pulls a sliver of 1.2 forward and makes this slice install
`cbor2`.

> **Answered: yes — exactly one**, `cases/positive/struct_text_keys.json`,
> derived by hand and transcribed from RFC 8949 Appendix A where it
> overlaps. The other fifteen schemas' vectors remain slice 1.2. If the
> PR contains a second case, that is scope creep and should be sent back.

**Q3 — Are integer-literal enumerations (`1 / 2 / 3`) in the §3 subset?**
§3 says "enumerations of literal values (e.g. `"red" / "green" / "blue"`)"
— the example is textual but the rule is not.

> **Answered: yes.** Promoted out of this plan to **D-008**, because it
> constrains the Phase 3 parser, the Phase 4 IR, and all three backends,
> none of which read this file. Consequences here: `enum.cddl` carries
> both kinds, and C-090 splits into C-090/C-091. Consequences elsewhere
> are in D-008 — notably that the parser must disambiguate `10 / 20 / 30`
> from a choice over named types and from a range, and that an
> integer-literal enum must encode the literal rather than an ordinal
> index (REQ-RT-385). Mixed-kind enumerations (`"red" / 2`) and negative
> literals stay out of the subset — as does the mixed-kind case, now
> stated in §3 rather than merely implied by its absence. The §3
> clarification merged in the same kickoff docs PR as REQ-RT-175/177.

**Q4 — How is Python pinned, and which version?** `requirements.txt` +
`pip install --require-hashes` (no new tooling, verbose) vs `uv` +
`uv.lock`. And which Python minor — `ubuntu-24.04`'s system Python, or
`actions/setup-python` pinned independently.

> **Answered: `requirements.txt` with hashes, and the runner's system
> Python**, documented as such in D-007 §4. No `actions/setup-python`:
> it would be a fourth pin class and a fifth SHA-pinned Action (D-006 §3)
> to decouple a version nothing here has a stated requirement on. The
> accepted consequence is that the Python minor moves when the runner
> image does — same shape as D-005, and attributable for the same reason.

**Q5 — Does the `conformance` CI job land in this slice or 1.2?**

> **Answered: here, non-required**, promoted to required when 1.2 gives it
> teeth. The objection — a job that is green over an almost-empty corpus
> is one people stop reading — is answered by §6: this slice's PR
> demonstrates the job failing, not just passing.

**Q6 — Is sixteen schemas the right granularity?** The alternative was
five or six larger schemas: fewer files, but a failing vector that is
ambiguous about which construct broke.

> **Answered: keep sixteen**, one construct group per file. Reversible
> now, expensive after 1.2 authors vectors against these names.

## 5. Spec conflicts found

None. No part of this slice requires editing `specs.md`, `design.md`, or
`code-style.md`, and none is edited.

Three **gaps** in specs.md were found at Phase 1 kickoff. Two were closed
by a docs PR that merged *before* this branch existed, so this slice is
implemented against a spec that states the rules its corpus encodes:

1. **JSON document form was undefined** — neither whitespace nor member
   order. Closed by **REQ-RT-175** and **REQ-RT-177** in §9.1. The second
   was found while drafting the first and is the more dangerous of the
   two: without it, three backends could each pick a different member
   order and every one of them would be "correct".
2. **§3's enumeration bullet was ambiguous about literal kind.** Closed by
   a §3 edit admitting text and unsigned-integer literals and excluding
   mixed-kind, negative, and float literals (D-008).
3. **§3 does not name recursive types**, though plan.md's slice 1.1 scope
   requires them and REQ-CDDL-090/097 presuppose them. *Left open
   deliberately* — handled in-corpus by C-102's `derives_from:
   REQ-CDDL-090`, since §3's "nested and forward type references"
   arguably covers it and a speculative edit to a frozen document is
   worse than a recorded derivation.

The ordering matters and was the point: had the corpus been authored
first, slice 1.2's ~60 expected JSON strings would have encoded a rule
found nowhere in the spec — and the cheapest way to resolve the first
backend that disagreed would have been to edit the corpus.

## 6. Tests first

The self-check *is* the test; there is no Rust in this slice. Each check
is written before the artifact it checks, so each one is observed failing.

| # | Check (`conformance/tools/check_corpus.py`) | Fails before | Passes after |
|---|---|---|---|
| 1 | `manifest.schema.json` validates against the JSON Schema 2020-12 metaschema | file absent / invalid `$schema` | schema authored |
| 2 | every file under `cases/` validates against `manifest.schema.json` | the worked case (Q2) written with a deliberate error — e.g. `"cbor": "a3 63 61"` with spaces, or a bare `36` where `{"uint":"36"}` is required | case corrected; both deliberate errors are kept as unit fixtures inside the tool's own tests, not as corpus files |
| 3 | `index.json` ⇔ the `cases/` and `schemas/` trees, set-equal both ways | a schema added to disk but not the index | index updated. Verified in both directions by temporarily removing an index entry and temporarily adding an unlisted file |
| 4 | every §3 bullet in `specs.md` is cited by ≥1 construct | `construct-coverage.json` authored with one bullet deliberately omitted | all bullets cited |
| 5 | every construct maps to ≥1 existing schema file | constructs listed before schemas exist | sixteen schemas authored |
| 6 | every construct's quoted bullet text occurs in `specs.md` §3 (whitespace-normalized), unless it carries `derives_from` | a quote altered by one word | quotes exact |
| 7 | `--check-format`: corpus JSON is 2-space, LF, trailing newline | a file saved compact | reformatted |

Check 4 is the DoD's load-bearing one and check 6 is what keeps it honest
over time: together they mean §3 and the corpus cannot drift apart without
CI saying so. Both are demonstrated failing in the PR body (development.md
§3.5 — a gate never seen red is a gate nobody has tested).

Not tested here, by design: that any expected byte is correct. Nothing
yet claims to be.
