# Slice 2.1 — The runtime contract

> Historical implementation plan, not normative. See specs.md, design.md,
> code-style.md, and decisions.md for the documents of record.

**Plan DoD** (from plan.md, quoted verbatim):

> The traits compile and are documented with compiling examples. Error
> types carry path, expected, found, and offset, asserted by unit tests. A
> trivial in-memory mock encoder/decoder pair round-trips a hand-built
> value, proving the contract is implementable without CBOR.

**Scope** (from plan.md, quoted verbatim):

> `Encoder`/`Decoder` traits and the `WireEncode`/`WireDecode` interface per
> §4.2. `EncodeError`/`DecodeError` carrying root-relative field paths,
> expected-vs-found, and input offsets.
>
> **Requirements.** REQ-RT-050, REQ-RT-060, REQ-RT-065, REQ-RT-090.

This is the first Rust in the project and the contract every backend targets
for the rest of its life: the Rust codecs in Phase 5, and the Java and C++
runtimes in Phases 7–8, which mirror it. development.md §4.1 marks it as a
slice the human writes and the AI reviews, and §6 asks that this be decided at
Phase 2 kickoff, so §5 Q1 is the first question and changes how this plan is
used. Nothing here implements a codec: no byte of CBOR or JSON is produced or
parsed, and no corpus vector is checked beyond the two vocabulary tests of §4.

Everything in §3 is a **proposal for the design to be argued with**, not a
finished design: the signatures are the shape I would write, with the
reasoning, so that review can attack the reasoning.

## 3. The proposed contract

### 3.1 `Encoder` and `WireEncode`

design.md §4.2 sketches five methods and "one per §8.1 primitive". The
complete list, with the reasoning for the parts the sketch leaves open:

```rust
pub trait Encoder {
    fn write_bool(&mut self, v: bool) -> Result<(), EncodeError>;
    fn write_u64(&mut self, v: u64) -> Result<(), EncodeError>;
    fn write_i64(&mut self, v: i64) -> Result<(), EncodeError>;
    fn write_f16(&mut self, v: f32) -> Result<(), EncodeError>; // §3.4: checks representability
    fn write_f32(&mut self, v: f32) -> Result<(), EncodeError>;
    fn write_f64(&mut self, v: f64) -> Result<(), EncodeError>;
    fn write_str(&mut self, v: &str) -> Result<(), EncodeError>;
    fn write_bytes(&mut self, v: &[u8]) -> Result<(), EncodeError>;
    fn write_null(&mut self) -> Result<(), EncodeError>;
    fn write_array_header(&mut self, len: usize) -> Result<(), EncodeError>;
    fn write_map_header(&mut self, len: usize) -> Result<(), EncodeError>;
    fn write_key_text(&mut self, key: &str) -> Result<(), EncodeError>;
    fn write_key_int(&mut self, key: u64) -> Result<(), EncodeError>;
}

pub trait WireEncode {
    fn encode<E: Encoder>(&self, e: &mut E) -> Result<(), EncodeError>;
}
```

- **Three float methods, not one**, because REQ-RT-178 judges "shortest
  digits" at the *held* width and REQ-RT-255 is about `float16`, so the
  encoder must know the declared width, which the value's Rust type (`f32`)
  does not say. (REQ-GEN-140 maps both `float16` and `float32` to `f32`.)
- **Keys are separate from values** (`write_key_*`), because JSON turns a
  key into a member name (a `uint` key becomes its decimal digits,
  REQ-KEY-030) while CBOR writes a typed key. A choice is `write_map_header(1)`
  plus a key plus a value (REQ-RT-360), an enum is its literal (REQ-RT-385):
  no further methods.
- **A length up front** for both headers (REQ-RT-340). JSON ignores it.
- **No `finish`/flush** in the trait: ownership of the sink is the concrete
  encoder's business.
- **Generic methods, not `dyn`.** `encode<E: Encoder>` monomorphises, which
  is what design.md §4.2 and §4.7 (no per-field indirection) intend. The
  price is that `WireEncode` is not object-safe, and the plan accepts it.

### 3.2 `Decoder`, `Key`, and `WireDecode`

design.md §4.5 shows `read_map_header()` then a loop of `read_key()`. That
cannot serve JSON (an object's length is unknown until its `}`) or an
indefinite-length CBOR map (REQ-RT-180), so the proposal replaces the header
with begin/next:

```rust
pub enum Key<'a> { Text(&'a str), Uint(u64) }

pub trait Decoder {
    fn read_bool(&mut self) -> Result<bool, DecodeError>;
    fn read_u64(&mut self) -> Result<u64, DecodeError>;
    fn read_i64(&mut self) -> Result<i64, DecodeError>;
    fn read_f16(&mut self) -> Result<f32, DecodeError>;   // accepts any float width (REQ-RT-180)
    fn read_f32(&mut self) -> Result<f32, DecodeError>;
    fn read_f64(&mut self) -> Result<f64, DecodeError>;
    fn read_str(&mut self) -> Result<&str, DecodeError>;      // valid UTF-8 (REQ-RT-315)
    fn read_bytes(&mut self) -> Result<&[u8], DecodeError>;
    fn read_null(&mut self) -> Result<(), DecodeError>;
    fn try_read_null(&mut self) -> Result<bool, DecodeError>; // consume a null if next, for `T / null`
    fn begin_array(&mut self) -> Result<Option<usize>, DecodeError>; // length hint, None if unknown
    fn next_element(&mut self) -> Result<bool, DecodeError>;         // false at the end
    fn begin_map(&mut self) -> Result<Option<usize>, DecodeError>;
    fn next_key(&mut self) -> Result<Option<Key<'_>>, DecodeError>;  // None at the end
    fn skip_value(&mut self) -> Result<(), DecodeError>;             // REQ-COMPAT-020
    fn position(&self) -> Position;                                  // for codec-raised errors
}

pub trait WireDecode: Sized {
    fn decode<D: Decoder>(d: &mut D) -> Result<Self, DecodeError>;
}
```

- **Borrowed returns** (`&str`, `&[u8]`, `Key<'_>`) borrow from the decoder, so
  a base64url or escaped-JSON string can use a decoder-owned scratch buffer
  and a CBOR string can point into the input. The generated codec copies into
  the DTO's owned `String` straight away (REQ-PERF-060: DTOs never borrow
  from the input), which is also the single allocation REQ-RT-280 wants. A
  codec must turn a `Key<'_>` into a field index *before* reading the value;
  design.md §4.7's length-then-compare dispatch fits that shape.
- **`begin_*` return a length hint, not a promise.** The hint feeds the
  clamped reservation of REQ-RT-280 (slice 2.5); a decoder with no length
  returns `None`.
- **Limits live inside the decoder** (design.md §4.5): `begin_array` and
  `begin_map` are where depth is counted and where 2.5 will refuse. The
  signature already allows it; this slice adds no enforcement.
- **`position()`** exists because the codec, not the decoder, raises errors
  such as a missing field, an unknown discriminant, or an out-of-range value,
  and they need an offset (REQ-RT-065).

### 3.3 Errors, paths, and positions

```rust
pub struct EncodeError { kind: EncodeErrorKind, path: Path }
pub struct DecodeError { kind: DecodeErrorKind, path: Path, position: Option<Position> }

pub enum DecodeErrorKind {
    // malformed (corpus classification)            // named as conformance/ names them
    Truncated, TrailingData, Syntax, InvalidUtf8, DuplicateKey,
    // well-formed but schema-invalid
    TypeMismatch { expected: ValueKind, found: ValueKind },
    MissingField { field: &'static str },
    NullNotAllowed, UnknownDiscriminant { found: String },
    InvalidChoice, OutOfRange, WrongLength { expected: usize, found: usize }, BadKey,
    // limits (enforced from slice 2.5)
    DepthExceeded, SizeExceeded,
}
pub enum EncodeErrorKind { NotRepresentable /* NaN, ∞, float16 */, OutOfRange }
pub enum ValueKind { Bool, Uint, Int, Float, Text, Bytes, Null, Array, Map, Tag, Other }
pub enum Position { Byte(u64), LineColumn { line: u32, column: u32 } }
```

- One `EncodeError` and one `DecodeError`, not an encoder-associated type,
  as design.md §4.2 and §7 decided: a codec must raise errors the encoder
  knows nothing about (range, `float16`, NaN to JSON).
- Variant names track the corpus `error.kind` enum one-for-one
  (`type_mismatch` → `TypeMismatch`, ...), so slice 2.3's harness maps by
  name and §4's test proves no corpus kind is unrepresentable. A stable
  `as_str()` returns the snake_case name; it is useful in diagnostics and is
  the hinge for that test.
- **Expected/found are `ValueKind`, not strings**, for the reasons
  rust-style.md gives (an enum where a closed set exists). JSON numbers and
  strings map onto the same kinds as their CBOR counterparts.
- **Paths are built on the way out** (§5 Q2): the codec writes
  `e.write_u64(self.age).map_err(|e| e.at_field("age"))?`, or the extension
  method `.at_field("age")` on the `Result`. No path is tracked on the happy
  path, so there is no per-field cost and no allocation until something
  fails (and the `Path` is a `Vec<PathSegment>` filled innermost-first and
  displayed outermost-first).
- `Display` renders `order.items[3].price: expected uint, found tstr (byte 147)`
  exactly as design.md §4.6 shows, with the REQ-RT-066 path grammar.

### 3.4 Where the checks live

- **`float16` representability (REQ-RT-255)**: in `Encoder::write_f16`, so
  that every encoding checks it and no codec can forget. The encoder
  returns `NotRepresentable`.
- **NaN/∞ to JSON (REQ-RT-210)**: the JSON encoder, in 2.4.
- **Range (REQ-RT-240/250)**: the generated codec, which is the only party
  that knows the range. The runtime ships two small helpers
  (`check_range_u64`-style, name to be settled in review) so the generated
  code is one line per ranged field and the error is built in one place.

## 5. Open questions — raised, and how they were answered

All ten were answered "as recommended"; each answer is recorded below the question.

**Q1 — Who writes 2.1?** development.md §4.1 designates it a slice you write
and the AI reviews ("traits, generics, associated types, error design"), and
says to delegate it with a thorough explain-the-diff pass if it proves too
steep, without reordering phases. §6 item 4 asks for this to be decided now.
**Options:** (a) you write it from §3, and I review for idiom and against the
requirements, and add the tests; (b) I implement it and give an
explain-the-diff walkthrough before merge; (c) split: I write the errors,
path, and tests (§3.3, §4 tests 1–4, 9–11) and you write the two traits and the
mock (§3.1–3.2, tests 5–8). **Recommendation: (c).** The traits are the
language-fluency material §4.1 means; the errors and path are mechanical and
are the part most worth having machine-checked against the corpus. If you'd
rather (a) or (b), say so; the plan holds either way.

> **Answered: (c), as recommended.** The AI writes `error.rs`, `path.rs`, `lib.rs`, the Cargo changes, and tests 1–4, 10 and 11; the human writes `Encoder`/`WireEncode`, `Decoder`/`Key`/`WireDecode` and the mock/sample codec (tests 5–8). Test 9 (`write_f16` on a non-half-representable value) needs a mock encoder, so it moves to the human's half. The AI half is delivered first, on the slice branch, so the traits can be written against real error types; the PR is opened when both halves are in. The split is recorded in the PR body.

**Q2 — How is the error path built?** (a) on unwind, with `.at_field(..)`
added by the generated code at each call (§3.3); (b) the encoder/decoder keeps
a path stack that codecs push to and pop from. **Recommendation: (a).** Zero
cost and zero allocation on the success path, which REQ-PERF and design.md
§4.7 want; (b) puts a push/pop pair around every field and still has to
clone the stack to build the error. The cost of (a) is that the generated code
must remember `.at_field` on every fallible call, which is mechanical and
testable (slice 5.3's DoD: the same errors on every negative vector).

> **Answered: (a), as recommended.** Paths are built on unwind with `.at_field(..)`.

**Q3 — Begin/next, or length-prefixed headers, on the decode side?** The
design sketch has `read_map_header()` returning a length. JSON and
indefinite-length CBOR (REQ-RT-180) cannot supply one up front.
**Recommendation: begin/next with an optional length hint (§3.2)**, recorded
in D-012 so design.md's sketch is superseded by the log. This is a deviation
from a document of record's illustration, not from a requirement; design.md
itself is not edited.

> **Answered: begin/next with a length hint, as recommended.** Recorded in D-012.

**Q4 — Where do the `float16` and range checks live?** §3.4: `float16` in the
encoder (one place, every encoding); range in generated code via a runtime
helper. **Recommendation: as §3.4.** The alternative of putting range data in
the encoder would turn the "compiled-in constants" of REQ-GEN-030 into a
runtime table.

> **Answered: as recommended.** `float16` representability in `Encoder::write_f16`; range in generated code via a runtime helper.

**Q5 — What does `Position` mean?** REQ-RT-065 says "the byte offset (CBOR) or
line/column (JSON) at which the problem occurred" and nothing else; D-010 left
it to this slice. For a truncated input, a duplicate key, and a wrong type the
natural answers differ. **Recommendation:** the offset of the *first byte of
the offending item*; for truncation, the offset at which the input ended; for
JSON, the 1-based line and column of the offending token's first byte, with the
column counted in UTF-8 bytes. Recorded in D-012. The corpus pins no offset
(D-010), so nothing here can be checked against it, and plan.md slice 2.3's
DoD ("expected error variant and input offset") will need reconciling then;
this is the third place that issue has been noted.

> **Answered: as recommended.** The offset of the first byte of the offending item; for truncation, where the input ended; JSON line/column 1-based, column in UTF-8 bytes. Recorded in D-012; the corpus pins no offset.

**Q6 — Is the error taxonomy the corpus's?** §3.3 mirrors the corpus's 13 kinds
plus two limit kinds. **Recommendation: yes**, and `as_str()` returns the
corpus spelling, so the harness needs no translation table. The corpus's
spelling thereby becomes a (soft) API commitment of the runtime; if you would
rather keep the runtime's variant names free, test 10 gets a mapping table
instead.

> **Answered: the corpus taxonomy, as recommended.** `as_str()` returns the corpus spelling.

**Q7 — `thiserror`?** rust-style.md says yes. It must support `no_std` (REQ-RT-110)
without losing `Error`; I believe thiserror 2 does, via `core::error::Error`,
but have not verified it against this toolchain. **Recommendation:** use
`thiserror` with `default-features = false`; if that does not build under
`no_std`, hand-write the two `Display`/`Error` impls (about 40 lines) and say
so in the PR. Either way no `std::error::Error` is required for the core.

> **Answered: `thiserror` without default features, as recommended**, with a hand-written fallback if it does not build under `no_std`.

**Q8 — Write the crate `no_std`-ready now?** `#![no_std]`, `extern crate
alloc`, an optional default `std` feature, `core`/`alloc` imports only
(rust-style.md). The `no_std` *target build* and CI job stay slice 2.7's.
**Recommendation: yes**, because retrofitting is a rewrite of every import and
the cost now is one attribute and a feature stanza. If you would rather not
carry the stanza until 2.7, say so.

> **Answered: `no_std`-ready now, as recommended**, with a default `std` feature; the `no_std` CI target stays slice 2.7's.

**Q9 — Include the corpus-vocabulary test (test 10)?** It adds `serde_json` as
a dev-dependency (MIT/Apache-2.0, already named in D-002 for `xtask`).
**Recommendation: yes.** It is the only link between this contract and
`conformance/`, it costs ~40 lines, and every later slice needs a corpus
reader anyway; I would keep the reader as a small test helper rather than a
crate until 2.2 shows what it needs.

> **Answered: include test 10, as recommended**, with `serde_json` as a dev-dependency.

**Q10 — Where do the mocks live?** `tests/mock_codec.rs`, test-only.
**Recommendation: yes.** A public `mock` module would become API and semver
surface (D-004) for no user.

> **Answered: mocks in `tests/`, as recommended.**

## 6. Spec conflicts and gaps found

No edit to `specs.md`, `design.md`, or `code-style.md` is required.

Gaps, handled as decisions in D-012 and not as spec edits:

- REQ-RT-065 leaves "the offset at which the problem occurred" undefined
  (Q5); REQ-RT-066 fixed the path but not the position.
- "Expected and found" has no stated content (Q6).
- design.md §4.5's `read_map_header()` cannot serve JSON or indefinite CBOR
  (Q3). It is an illustration, so this is a deviation recorded in the log, not
  a conflict with a requirement.

**The risk this plan carries forward.** This contract is designed with no
encoder or decoder behind it, and it is the one thing every backend inherits.
The plan's mitigation is sequencing: 2.2 (CBOR encoder), 2.3 (CBOR decoder) and
2.4 (JSON) each exercise it against the corpus, and a change they force is
cheaper now than after Phase 5. The PR for 2.1 should say that a signature
change in 2.2–2.4 is expected and cheap, and that a change after 5.3 is not.
