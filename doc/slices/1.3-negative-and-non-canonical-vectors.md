# Slice 1.3 — Negative and non-canonical vectors

> Historical implementation plan, not normative. See specs.md, design.md,
> code-style.md, and decisions.md for the documents of record.

**Plan DoD** (from plan.md, quoted verbatim):

> Every negative vector is classified as either *malformed CBOR* or
> *well-formed but schema-invalid*, and the self-check confirms the
> classification against the independent implementation. Every
> non-canonical input is confirmed to be valid CBOR that a conforming
> decoder must accept.

**Scope** (from plan.md, quoted verbatim, including the requirement list
extended by PR #7):

> Author negative decode vectors: type mismatches, missing required fields,
> duplicate keys, truncated input, invalid UTF-8, bad discriminants,
> out-of-range values, explicit null on a non-nullable optional. Author
> non-canonical but valid inputs that decoders must accept: indefinite
> lengths, unsorted keys.
>
> **Requirements.** REQ-RT-300, REQ-RT-310, REQ-RT-315, REQ-RT-380,
> REQ-RT-240, REQ-RT-350, REQ-RT-180; plus the encode-error and decode-only
> vectors deferred from 1.2 (one record-shape decision for all of them):
> REQ-RT-080, REQ-RT-210, REQ-RT-250, REQ-RT-255, and the decode halves of
> REQ-RT-175, REQ-RT-178, REQ-RT-179, REQ-RT-200, REQ-RT-220.

Slice 1.2 gave the corpus its *positive* half: values that must encode to
exactly these bytes. This slice gives it the half that says what a decoder
must reject, what it must nonetheless accept, and what an encoder must
refuse to emit. Three things are new and none was settled by D-007, which
only reserved the kind names: (a) the record shapes, (b) what an expected
*error* is allowed to pin, and (c) how the self-check confirms a
classification without a CDDL parser. §6 asks about each. Two spec gaps
(§6 Q1, Q2) should be closed by a docs PR before implementation, the same
way #5 and #7 preceded 1.1 and 1.2.

## 3. Record shapes

All records share `id`, `root`, `description`, `requirements`, `derivation`
with the positive record. `input` is an object with **exactly one** member,
`cbor` (lowercase hex, no separators) or `json` (exact text, as a JSON
string).

### 3.1 `negative` — a decode that must fail

```json
{ "id": "struct_text_keys/age_is_text",
  "root": "Person",
  "description": "age holds a tstr",
  "requirements": ["REQ-RT-060"],
  "derivation": "cbor2",
  "input": { "cbor": "a2…" },
  "classification": "schema_invalid",
  "error": { "kind": "type_mismatch", "path": "age" } }
```

- `classification` is `malformed` or `schema_invalid` (the DoD's two
  values). §6 Q3 pins which side duplicate keys and invalid UTF-8 fall on.
- `error.kind` is a closed enum, and each kind belongs to exactly one
  classification (checked):
  - malformed: `truncated`, `trailing_data`, `syntax`, `invalid_utf8`, `duplicate_key`
  - schema_invalid: `type_mismatch`, `missing_field`, `null_not_allowed`,
    `unknown_discriminant`, `invalid_choice`, `out_of_range`, `wrong_length`, `bad_key`
- `error.path` (schema_invalid only; §6 Q1): REQ-RT-065's path from the DTO
  root.
- Optional `error.discriminant` (REQ-RT-380 requires the offending
  discriminant be identified) and `error.constraint` (the schema's range text,
  e.g. `"0..255"`, for `out_of_range`; checked to occur in the schema, §5).
- **No error offset, no message text.** §6 Q1 and Q5.

### 3.2 `noncanonical` — an input a decoder must accept

```json
{ "id": "array_homogeneous/numbers_indefinite",
  "root": "Numbers", "description": "…", "requirements": ["REQ-RT-180"],
  "derivation": "hand-encoded",
  "variance": "indefinite_length",
  "input": { "cbor": "9f010203ff" },
  "value": { "array": [ … ] },
  "cbor": "83010203",
  "json": "[1,2,3]" }
```

`value`, `cbor`, `json` are the positive-record triple for the value the
input decodes to, so every accepted input is tied to a canonical vector and
a decoder can be tested as *decode(input) == decode(canonical)* in either
encoding. `variance` names the way the input departs from canonical form;
the closed enum is:

- CBOR: `indefinite_length`, `unsorted_keys`, `non_shortest_head`,
  `wider_float`, `non_canonical_nan`
- JSON: `whitespace`, `string_escapes`, `number_spelling`,
  `int_as_string`, `int_as_number`, `base64_padding`
- JSON, added by Q2: `member_order` (REQ-RT-176)
- either: `absent_default` (REQ-RT-080)

Record `value` lists a map's pairs in **canonical** order even when the input
is unsorted; the input is what is unsorted.

### 3.3 `encode_error` — an encode that must fail (§6 Q4)

```json
{ "id": "json_edge/ratio_nan",
  "root": "Edge", "description": "…", "requirements": ["REQ-RT-210", "REQ-RT-172"],
  "derivation": "cbor2",
  "value": { "map": [ … ] },
  "expect": {
    "cbor": "a4…f97e00…",
    "json": { "error": { "kind": "not_representable", "path": "ratio" } } } }
```

`expect` has `cbor` and `json` members; each is either the expected
output (hex / text) or `{"error": …}`, and at least one is an error. The
NaN case is why this is one record rather than an error and a separate
positive: encoding NaN to CBOR must succeed and give `f97e00`
(REQ-RT-172), while encoding it to JSON must raise (REQ-RT-210). Error
kinds: `not_representable` (210, 255), `out_of_range` (250).

## 4. How the self-check confirms a classification (DoD clause 1)

The 1.2 `cborcheck.check` stops at the first thing it cannot parse and
treats every deviation as one list. That is enough to say "this positive
vector is canonical" and not enough to say *why* a negative input is
rejected. `cborcheck.analyze(data)` returns four disjoint finding lists:

| List | Contents (all from RFC 8949) |
|---|---|
| `malformed` | truncation, reserved additional information, stray break, unterminated or wrongly-chunked indefinite item, trailing bytes |
| `invalid` | text string not valid UTF-8 (§1.2 "invalid" items), duplicate map key |
| `nondeterministic` | each tagged with a category: `indefinite`, `head`, `float`, `nan`, `key_order` |
| `outside_subset` | tags, `undefined`, simple values other than false/true/null (a positive vector fails on this, a negative one does not) |

Indefinite lengths are *parsed* now (chunks of the matching major type until
`break`), because the non-canonical vectors contain them and the remaining
findings have to be found inside them.

**Classification rule** (§6 Q3 recommendation): *malformed* ⇔
`analyze.malformed` or `analyze.invalid` is non-empty. *schema_invalid* ⇔
both are empty — the input is a well-formed, valid CBOR item that is simply
not an instance of `root`. Confirmed against `cbor2` independently:

- `malformed` with kind `truncated`/`trailing_data`/`syntax`: `cbor2.loads` **must
  also fail** (two independent parsers agree);
- `malformed` with kind `invalid_utf8`: `cbor2.loads` must fail (it validates
  UTF-8); with kind `duplicate_key`: `cbor2.loads` *succeeds* (it keeps
  the last value), so only `analyze` and a direct duplicate-key walk
  over the decoded pairs confirm it — stated in the check, not hidden;
- `schema_invalid`: `cbor2.loads` **succeeds** and `analyze` finds nothing.

For JSON the same rule applies with Python's `json` module in strict mode
(`parse_constant` rejecting `NaN`/`Infinity`, an `object_pairs_hook` rejecting
duplicates, bytes decoded as UTF-8 first).

What this does **not** establish is that a `schema_invalid` input really is
not an instance of its `root` — that needs a CDDL validator, which would
be Lido code (D-007 §3, 1.2 plan Q7). The partial mitigations are: every
negative carries a typed `kind` and a `path`, so a reviewer can read the
claim against the 4-line schema; the *same* bytes as a positive base case
with one change are used wherever possible (derivation notes name the
base case); and the first Phase 3 slice with a validator adds "every
negative input is rejected, every positive accepted" outside the zero-Lido
gate. The PR body says this plainly.

Non-canonical (DoD clause 2): for every `noncanonical` CBOR input —
`cbor2.loads` succeeds; `analyze.malformed` and `.invalid` are empty
(valid, hence must be accepted); the `nondeterministic` findings contain
the category that matches the declared `variance` (so the input is
*actually* non-canonical in the claimed way, and the claim cannot rot);
the decoded value equals `value` (map order ignored, because order is the
variance); and `cbor2.dumps(value, canonical=True)` equals `cbor` with
`cborcheck` clean. For JSON: strict parse succeeds; the input differs from
`json` textually; and `json_equivalent(input, json, variance)` holds — it
parses both and walks them together, allowing exactly the leaf-level
relaxation the variance names (ints-as-strings, padding, numeric spelling),
and nothing else.

## 6. Open questions — raised, and how they were answered

All nine were answered "as recommended"; each answer is recorded below the question.

**Q1 — What does an expected decode error pin?** REQ-RT-065 requires every
error to carry a path, "expected and found", and a byte offset (CBOR) or
line/column (JSON). The spec fixes one path example (`order.items[3].price`)
and nothing else, and these things are undefined: the path of an error *at
the root*; the segment for an integer-keyed field (`9`? `"9"`? a name — the
schema has none); the segment for a table entry; and what "the offset at
which the problem occurred" means (start of the offending item, or where a
decoder noticed — they differ for a duplicate key and for a truncated
string). **Options:** (a) vectors pin `classification` and `error.kind`
only; (b) also pin `path`, after a docs PR defines the grammar; (c) pin
`path` now, only for the two segment forms the spec illustrates (struct
field, array index) and avoid the undefined ones. **Recommendation: (b)**,
as a small docs PR before implementation: field names joined by `.`, array
elements `[n]`, table entries `[key]` (`["a"]` / `[7]`), integer-keyed
fields by decimal key, root is the empty path; and offset *not* pinned
(stays undefined until slice 2.1 designs the error types, where it belongs).
(c) would work for ~90% of the vectors and leave the rest silently
inconsistent; (a) discards what REQ-RT-065 is for.

> **Answered: (b), as recommended.** A docs PR (#9) adds **REQ-RT-066** (path grammar) before implementation. Vectors pin `error.kind` and, for `schema_invalid`, `error.path` in that grammar; table-entry paths are `["a"]` / `[7]`, integer-keyed fields use their decimal key, the root is `""`. Offsets are not pinned. Implementation does not start until #9 has merged.

**Q2 — Must a JSON decoder accept members in any order?** REQ-RT-177
governs *emitting* order; REQ-RT-180 makes CBOR decoders accept unsorted
keys; nothing says the same for JSON. A `noncanonical` JSON vector with
shuffled members would pin a rule the spec lacks. **Recommendation:** add
it to the Q1 docs PR as one sentence in §9.1 (decoders accept members in any
order, mirroring REQ-RT-180), then author the vector. Alternative: omit the
vector and leave the question open — rejected, because three backends will
each answer it and one will answer wrongly.

> **Answered: add the sentence, as recommended.** The same docs PR adds **REQ-RT-176** (JSON decoders accept members in any order). A shuffled-member `noncanonical` JSON vector (`variance: member_order`, added to the enum) is authored against it.

**Q3 — Where do duplicate keys and invalid UTF-8 fall in the two-way
classification?** RFC 8949 distinguishes *not well-formed* from
*well-formed but invalid*, and puts both of these in the second group; the
DoD's second group is "schema-invalid". Neither is about the schema.
**Options:** (a) `malformed` includes anything a strict generic CBOR/JSON
decoder rejects, so invalid UTF-8 and duplicate keys are `malformed`;
(b) `schema_invalid` is "well-formed", so they are `schema_invalid`;
(c) a third value `invalid`. **Recommendation: (a)**: it keeps the DoD's
two values, matches how REQ-RT-300/315 phrase them (rejected before any
schema is consulted), and gives a clean test for harness authors — "did a
generic strict decoder reject this?". Recorded in D-010 and the README so
the word *malformed* is not read in the narrow RFC sense.

> **Answered: (a), as recommended.** `malformed` means "rejected by a strict generic CBOR/JSON decoder", which includes invalid UTF-8 and duplicate keys. Recorded in D-010 and the README.

**Q4 — A new `encode_error` kind (a new directory and enum value).** D-007
reserved `negative`, `noncanonical`, `evolution`. The DoD calls every
*negative* vector either malformed or schema-invalid, which is false of an
encode failure, so encode errors cannot be `negative` without weakening the
DoD. **Options:** (a) new kind `encode_error`; (b) a `negative` record with
`operation: "encode"` and a third classification; (c) skip encode errors.
**Recommendation: (a)**, recorded in D-010; `manifest_version` stays 1
because no harness exists yet to be broken by an unknown kind (the first is
Phase 2), and the version bump rule (D-007 Consequences) exists to protect
consumers. If you read that rule as covering any format growth, say so and
the PR bumps it to 2 with the matching D-010 clause.

> **Answered: (a), as recommended.** New kind `encode_error`, recorded in D-010; `manifest_version` stays 1.

**Q5 — Do vectors pin error message text?** No. **Recommendation:** no,
and say so in the README, because message text is language-idiomatic and
REQ-RT-065 specifies content, not wording.

> **Answered: no message text is pinned**, as recommended.

**Q6 — Numeric coercions the spec does not state.** (i) CBOR integer into a
`float` field and (ii) a half/single float whose value is not exactly
representable into a `float16` field, on *decode*. REQ-RT-060 forbids
"silently coercing", REQ-RT-255 is encode-only, and nothing says whether
CBOR `1` is a valid `float64`. **Recommendation:** no vectors; list both
in the PR body and in the Q1 docs PR only if you want them decided now.
They are the sort of thing the first backend will decide by accident.

> **Answered: no vectors, as recommended.** Both coercions are listed in the PR body as unspecified.

**Q7 — Who owns REQ-RT-270/280/290 (limits)?** They are in §9.4, so slice
1.4's coverage check ("every requirement in §9.1–§9.8 maps to a case") fails
unless some case exists, and the corpus has no way to express a limit
setting. **Options:** (a) add an optional `limits` object to the record
(`{"max_depth": 4}`) and author three small negatives; (b) have 1.4 exempt
them in `coverage.json` with a stated reason; (c) leave to a later slice.
**Recommendation: (b)**, decided at 1.4, because (a) bakes a configuration
vocabulary (what are the names? the defaults?) into a format three
languages read before any of them has a limits API; slice 2.1 designs
that, and a corpus field guessed in advance would be the thing everyone
then conforms to. Flagged here so that 1.4's plan inherits it.

> **Answered: (b), as recommended.** Slice 1.4's plan inherits it: REQ-RT-270/280/290 are exempted in `coverage.json` with a stated reason, and no `limits` field is added to the format here.

**Q8 — Verification gap for `schema_invalid` and `out_of_range`.** §4: the
harness cannot prove a `schema_invalid` input is outside its root's shape
without a validator. For ranges it can do a little better (the `constraint`
text must appear in the schema and the number must lie outside it).
**Recommendation:** accept, state it in the PR body, and track the
Phase 3 corpus-validates-against-schemas check as one item covering both
positive (1.2 Q7) and negative vectors.

> **Answered: accept, as recommended.** The PR body states the gap; the Phase 3 corpus-validates-against-schemas check covers positive and negative vectors together.

**Q9 — One PR or two?** ~95 vectors plus a schema, a parser refactor, and
three record shapes is the biggest slice so far. **Recommendation: one
PR, but in this commit order so review can stop anywhere:** record shapes +
`analyze` + checks 15–16 (no vectors); then negatives; then noncanonical;
then encode_error. If you would rather split, the natural line is
negative+noncanonical (the DoD) vs. encode_error (carried over from 1.2),
and plan.md's 1.3 requirement list would move REQ-RT-210/250/255 to a new
slice.

> **Answered: one PR, in the stated commit order, as recommended.**

## 7. Spec conflicts and gaps found

No edit to `specs.md`, `design.md`, or `code-style.md` is required: Q1 and
Q2 were answered by a separate docs PR (#9, REQ-RT-066 and REQ-RT-176),
which must merge before implementation starts.

Gaps found and deliberately not vectorised (no spec text to test against):
JSON lone-surrogate escapes (`"\ud800"`); standard-alphabet base64
(`+`, `/`) on decode of a `bstr`; integer-for-float and float16-narrowing on
CBOR decode (Q6); error offsets (Q1).

Noted, not a conflict: REQ-RT-310 requires the decoder not read beyond the
buffer; that is a property of an implementation, not of an input, and no
vector can assert it. The truncation vectors are necessary for it and not
sufficient; Phase 2 adds fuzzing (REQ-RT-310's real test) and 1.4's
coverage entry should say so.
